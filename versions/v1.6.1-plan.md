# v1.6.1 版本计划：酒店水单、多账本基础与多语言扩展

更新日期：2026-06-25
文档状态：设计草案 / Draft
内部开发线：v1.6.1
App Store 对外版本：ASC 1.5.0（商店不区分内部小版本）
承接版本：v1.6.0
当前落地范围：酒店水单 A 阶段、多账本基础能力、新一轮多语言支持（含日文支持）、跨平台 App Icon 重绘

## 1. 版本定位

`v1.6.1` 承接 `v1.6.0 / ASC 1.5.0` 已进入发布维护态后的下一条内部开发线。`v1.6.0` 的 Xcode Cloud、TestFlight、schema 和截图门禁不再作为本版本功能开发 blocker；商店侧继续使用 ASC 1.5.0 作为对外版本，不通过 `MARKETING_VERSION` 区分内部小版本。`v1.6.1` 功能是否随 ASC 1.5.0 的后续构建进入 TestFlight 或正式发布，需要由 release gate 单独决定。

本版本规划三条主线：

1. 酒店水单识别与酒店消费归档：macOS 端优先，从用户手动导入 PDF 开始。
2. 多账本基础能力：承接 `v1.5.0 / v1.5.1` 顺延的基础账本模型、默认账本迁移和账本切换。
3. 新一轮多语言支持：补齐新增功能的三语文案，并将日文支持纳入本版本落地范围。
4. 跨平台 App Icon 重绘：保留钱包、金币、闪电和蓝绿背景元素，但为 iOS、Apple Watch、tvOS、visionOS 分别生成平台专用图标资产，避免闪电在横向或分层平台上被压成细线。

酒店水单功能不是把酒店水单简单 OCR 成一笔金额，而是把一次入住整理为可复核、可归档、可统计的酒店消费记录。目标字段包括酒店名称、品牌 / 集团、城市 / 国家、入住日期、退房日期、房晚、房型、确认号 / 订单号、房费、税费、服务费、餐饮消费、其他消费、总额、支付方式、来源和识别置信度。

酒店水单当前只规划 A 阶段。B 阶段本地邮箱半自动导入、C 阶段 Worker 云端自动化只作为后续路线记录，不进入当前版本实现范围。

## 2. 功能目标

酒店水单目标：

- 在 macOS 新增“酒店消费”模块。
- 支持用户手动拖入或选择本地酒店水单 PDF。
- 使用 PDFKit 提取 PDF 文本。
- 将提取文本传入现有外部模型解析管线。
- 将模型结果约束为酒店水单 schema。
- 生成待确认的 `HotelStayDraft`。
- 提供可编辑识别结果确认页。
- 用户确认后创建正式 `HotelStayRecord`。
- 用户确认后同时生成或关联一条普通支出 `Transaction`。
- 提供酒店消费列表页和详情页。
- 预留 `sourceType` 和 import pipeline，便于后续接入本地邮箱、Worker、分享扩展等来源。

多账本基础目标：

- 新增基础 `LedgerProfile` / 账本模型。
- 为现有单一正式账本建立默认账本迁移路径。
- 为 `Transaction` 预留或落地 `ledgerId` 归属字段。
- 新建、重命名、归档账本，并设置默认账本。
- 支持在 iPhone / iPad / Mac 查看当前账本或全部账本。
- 新增账单时默认写入当前账本或默认账本。
- 支持将既有账单移动到另一个账本。
- 统计、导入、订阅和酒店消费都需要明确账本口径。

多语言支持目标：

- 新增 `v1.6.1` 全功能的 `zh-Hans` / `zh-Hant` / `en` 文案覆盖。
- 新增 `ja` 日文支持，覆盖 App 内关键路径、截图文案、ASC 元数据和 Review Notes。
- 审计硬编码字符串，优先收口新模块和高频主路径。
- 对酒店消费、多账本、设置、错误提示、Review Notes 和截图文案建立本地化清单。
- `ko` 作为后续候选，不进入 `v1.6.1` P0。
- 语言扩展必须使用本地化截图 / 元数据 / 审核说明，不把机器翻译原样作为发布文案。

当前非目标：

- 不实现邮箱自动拉取。
- 不实现后台自动任务。
- 不实现 Worker 自动化。
- 不自动正式入账。
- 不绕过用户确认直接写入正式账本。
- 不把酒店水单能力扩展为通用差旅管理系统。
- 不实现家庭共享账本、多人协作、权限管理或团队账本。
- 不实现多币种资产管理、预算系统或复杂财务报表。
- 不把 Watch / Widget / tvOS / visionOS 在本版本扩展为完整多账本编辑端。
- 不在没有人工审校的情况下直接发布新语言商店元数据。

## 3. 分阶段路线

### 3.1 A 阶段：手动导入 PDF 识别

A 阶段是酒店水单主线的当前优先实现阶段，也是酒店水单在 `v1.6.1` 中唯一规划的落地范围。

功能范围：

- macOS 新增“酒店消费”模块。
- 支持用户拖入或选择本地酒店水单 PDF。
- 使用 PDFKit 提取 PDF 文本。
- 将提取文本传入现有外部模型解析管线。
- 解析为结构化酒店水单字段。
- 生成 `HotelStayDraft`。
- 展示可编辑的识别结果。
- 用户确认后创建 `HotelStayRecord`。
- 同时生成一条关联的普通支出 `Transaction`。
- 新增酒店消费列表页和详情页。
- 不实现邮箱自动拉取。
- 不实现后台自动任务。
- 不实现 Worker 自动化。
- 预留 `sourceType` 和 import pipeline，方便后续扩展。

建议处理流程：

```text
Local PDF
-> PDFKit text extraction
-> HotelFolioParsePipeline
-> HotelStayDraft(status: needsReview)
-> User Review
-> HotelStayRecord + linked Transaction
```

### 3.2 B 阶段：本地邮箱半自动导入

B 阶段是面向公共用户的下一阶段能力，不进入 `v1.6.1` 当前实现范围。

功能范围：

- 用户主动点击 App 内的“扫描邮箱水单”。
- macOS App 本地连接 QQ 邮箱 / IMAP。
- 邮箱授权码只存储在本机 Keychain。
- 搜索酒店水单相关邮件。
- 下载 PDF 附件。
- 本地提取 PDF 文本。
- 脱敏后调用云模型识别。
- 识别结果进入“待确认”。
- 用户确认后才正式入账。
- 不在云端保存邮箱授权。
- 不自动持续扫描邮箱。
- 不直接自动入账。

B 阶段隐私原则：

- 邮箱授权码不上传云端。
- 邮件拉取在本机完成。
- 云端只处理脱敏后的账单文本。
- 用户主动点击后才扫描。
- 所有结果需要用户确认后才写入正式账本。

### 3.3 C 阶段：Worker 云端自动化扩展

C 阶段是后续高级能力，优先作为个人自用或订阅用户灰度功能，不作为公共用户主链路。

功能范围：

- Worker 云端定时发现酒店水单。
- 自动识别 PDF。
- 将结构化结果推送给用户。
- App 中生成“待确认酒店消费”。
- 用户确认后才正式入账。

C 阶段限制：

- 不默认开放给所有用户。
- 不自动正式入账，只生成待确认记录。
- 需要处理邮箱授权失效、IMAP 风控、重复邮件、PDF 格式差异、推送失败、隐私合规和云端存储风险。
- 如涉及云端存储原始 PDF、原始邮件或完整账单文本，必须重新做隐私与合规评审。

## 4. 架构原则

识别管线不应关心来源。A/B/C 的区别只是输入来源不同：

- A：PDF 来自用户拖拽或文件选择。
- B：PDF 来自 macOS 本地邮箱扫描。
- C：PDF 或结构化结果来自 Worker。

统一处理流程：

```text
PDF / Text Input
-> HotelFolioParsePipeline
-> HotelStayDraft
-> User Review
-> HotelStayRecord + Transaction
```

建议预留来源类型：

```swift
enum HotelFolioSourceType {
    case manualPDF
    case localEmailIMAP
    case cloudWorker
    case shareExtension
}
```

设计约束：

- `HotelFolioParsePipeline` 接受 PDF 文本或已经提取好的文本输入，不直接依赖文件选择器、邮箱客户端或 Worker。
- 来源适配层负责读取文件、拉取附件、权限处理、去重标记和初始 import metadata。
- 解析层只负责把酒店水单文本变成结构化候选结果。
- 正式入账层只接受用户确认后的 `HotelStayRecord`，不得直接接受模型输出。
- `Transaction` 仍是通用账本流水；酒店消费作为专业档案通过可选关联字段挂接。

## 5. 数据模型建议

### 5.1 HotelStayDraft

`HotelStayDraft` 用于存储识别后的待确认结果，不直接污染正式账本。

建议状态：

```swift
enum HotelStayDraftStatus {
    case imported
    case textExtracted
    case parsed
    case needsReview
    case confirmed
    case rejected
    case postedToLedger
}
```

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 草稿 ID |
| `sourceType` | 来源类型，使用 `HotelFolioSourceType` |
| `targetLedgerId` | 目标账本 ID，默认使用当前账本或默认账本 |
| `sourceFileName` | 本地 PDF 文件名，可为空 |
| `sourceEmailSubject` | 邮件主题，B/C 阶段可用 |
| `sourceEmailFrom` | 发件人，B/C 阶段可用，展示前需脱敏 |
| `rawText` | PDFKit 提取或来源传入的原始文本 |
| `parsedPayload` | 模型解析后的结构化 payload |
| `confidence` | 识别置信度 |
| `status` | 草稿状态 |
| `createdAt` | 创建时间 |
| `updatedAt` | 更新时间 |

状态约束：

- `imported`：来源已登记，但尚未完成文本提取。
- `textExtracted`：PDF 文本已提取。
- `parsed`：模型或规则已输出结构化候选。
- `needsReview`：需要用户确认或补字段。
- `confirmed`：用户已确认酒店消费内容。
- `rejected`：用户拒绝或删除该识别结果。
- `postedToLedger`：已生成正式 `HotelStayRecord` 并关联普通流水。

### 5.2 HotelStayRecord

`HotelStayRecord` 用于存储用户确认后的正式酒店消费记录。

建议字段：

| 字段 | 说明 |
|---|---|
| `id` | 酒店消费记录 ID |
| `ledgerId` | 所属账本 ID，应与关联普通流水一致 |
| `linkedTransactionId` | 关联普通支出流水 ID |
| `hotelName` | 酒店名称 |
| `hotelGroup` | 酒店集团 |
| `hotelBrand` | 酒店品牌 |
| `city` | 城市 |
| `country` | 国家 |
| `checkInDate` | 入住日期 |
| `checkOutDate` | 退房日期 |
| `nights` | 房晚数 |
| `roomType` | 房型 |
| `confirmationNumber` | 确认号 / 订单号 |
| `currency` | 币种 |
| `roomCharge` | 房费 |
| `taxAmount` | 税费 |
| `serviceCharge` | 服务费 |
| `foodBeverageAmount` | 餐饮消费 |
| `otherAmount` | 其他消费 |
| `totalAmount` | 总额 |
| `paymentMethod` | 支付方式 |
| `sourceType` | 来源类型 |
| `sourceFileName` | 来源文件名 |
| `confidence` | 最终识别置信度 |
| `rawText` | 原始识别文本，需允许用户查看和删除 |
| `createdAt` | 创建时间 |
| `updatedAt` | 更新时间 |

正式记录约束：

- `HotelStayRecord` 必须来自用户确认后的草稿或用户手动补全。
- 低置信字段应在确认页明显提示，不应静默写入正式记录。
- 删除 `HotelStayRecord` 时，需要明确是否同时删除或保留关联的普通 `Transaction`。

## 6. Transaction 关联

普通记账流水中建议预留可选关联字段：

```swift
hotelStayRecordId: UUID?
```

酒店消费确认后，应生成或关联一条普通支出流水：

| Transaction 字段 | 建议取值 |
|---|---|
| `type` | `expense` |
| `amount` | `HotelStayRecord.totalAmount` |
| `merchant` | `HotelStayRecord.hotelName` |
| `category` | `travel` / `accommodation` / `酒店住宿` |
| `date` | 优先使用 `checkOutDate`，如水单有明确账单日期可用账单日期 |
| `note` | 入住日期、退房日期、房型、订单号等摘要信息 |
| `hotelStayRecordId` | 当前 `HotelStayRecord.id` |

设计注意：

- 用户确认酒店消费时可选择“同时入账”或“只保存酒店消费记录”，但默认建议同时生成普通支出流水。
- 如用户手动关联已有 `Transaction`，不得重复生成新流水。
- 酒店消费详情页应能跳转到关联流水；账单详情页也应能跳转回酒店消费记录。

## 7. 识别 Schema 建议

酒店水单解析目标字段：

```json
{
  "hotel_name": "",
  "brand": "",
  "group": "",
  "city": "",
  "country": "",
  "check_in_date": "",
  "check_out_date": "",
  "nights": 0,
  "room_type": "",
  "confirmation_number": "",
  "currency": "",
  "room_charge": 0,
  "tax": 0,
  "service_charge": 0,
  "food_beverage": 0,
  "other_charges": 0,
  "total_amount": 0,
  "payment_method": "",
  "confidence": 0,
  "raw_text_excerpt": ""
}
```

解析要求：

- 日期字段应保留原始文本证据，并尽量标准化为 ISO-8601。
- 金额字段应保留币种，不同币种不得直接相加。
- `room_charge + tax + service_charge + food_beverage + other_charges` 与 `total_amount` 不一致时进入 `needsReview`。
- `confidence` 低于阈值时不得默认正式入账。
- `raw_text_excerpt` 只用于帮助用户复核，不应替代完整原始文本查看能力。

## 9. 隐私和安全要求

必须满足：

- A 阶段只处理用户主动选择的本地 PDF。
- B 阶段邮箱授权码只保存在本地 Keychain。
- 不允许把邮箱授权码上传到云端。
- 不允许把完整邮箱内容上传到云端。
- 云模型识别前应尽量脱敏。
- 需要脱敏邮箱、手机号、会员号、身份证 / 护照号、银行卡号等敏感信息。
- 所有识别结果默认进入待确认状态。
- 用户确认后才正式入账。
- 需要支持删除 `HotelStayDraft` 和 `HotelStayRecord`。
- 需要支持用户查看识别来源和原始文本。
- 审核说明中需要提供示例 PDF 或 Demo Mode，避免审核员必须登录真实邮箱才能测试。

额外要求：

- 调试日志不得记录完整原始水单文本、完整邮箱内容、授权码或未脱敏证件号。
- 如后续接入云模型，发送前应进行最小化裁剪，只发送解析所需的账单文本片段。
- Demo Mode 应使用虚构酒店、虚构订单号、虚构金额和虚构邮箱，不使用真实用户材料。
- 用户删除酒店消费记录时，应提供清晰文案说明是否同时删除关联普通流水。

## 10. 多账本基础能力

多账本是 `v1.5.0 / v1.5.1` 明确顺延的基础能力。`v1.6.1` 只做最小可用的个人多账本，不做家庭共享、多人协作、权限、团队空间或复杂资产管理。

### 10.1 产品范围

当前版本优先实现：

- 创建账本。
- 重命名账本。
- 归档账本。
- 设置默认账本。
- 查看当前账本。
- 查看全部账本聚合。
- 将单笔账单移动到其他账本。
- 导入、语音、快捷指令和分享扩展新增账单时写入默认账本。
- iPad / Mac 工作台支持账本切换。
- 月报 / 统计支持当前账本和全部账本两种口径。

当前版本不做：

- 家庭共享账本。
- 多用户权限。
- 账本邀请。
- 账本级云空间或独立 iCloud container。
- 账本级自定义分类 / 来源的完整隔离。
- Watch / Widget / tvOS / visionOS 的复杂账本切换。
- 多币种资产折算、预算、负债、报销审批或企业财务。

### 10.2 数据模型方向

建议新增 `LedgerProfile`：

| 字段 | 说明 |
|---|---|
| `id` | 账本 ID |
| `name` | 账本名称 |
| `iconName` | 图标名称，可选 |
| `colorName` | 主题色名称，可选 |
| `currency` | 默认币种，可选；首版不做自动换算 |
| `isDefault` | 是否默认账本 |
| `sortOrder` | 排序 |
| `archivedAt` | 归档时间，可为空 |
| `createdAt` | 创建时间 |
| `updatedAt` | 更新时间 |

建议为 `Transaction` 增加账本归属：

```swift
ledgerId: UUID?
```

迁移策略：

- 创建一个默认账本，例如“个人账本”。
- 旧数据中 `ledgerId == nil` 的账单在读取时视为默认账本。
- 新增账单必须写入明确 `ledgerId`。
- 可在后续迁移中分批把旧账单回填为默认账本 ID。
- `BackupBundle` / JSON 导出需要包含 `LedgerProfile` 和账单 `ledgerId`。
- CloudKit 需要同步 `LedgerProfile`，并让 `LedgerTransaction` 带账本归属字段。

### 10.3 与现有模块的关系

账单导入：

- 截图、剪贴板、语音、快捷指令、分享扩展默认写入当前账本或默认账本。
- 低置信候选进入确认页时允许选择目标账本。
- 批量导入队列项应保存 `targetLedgerId`，确认入账后写入对应账本。

订阅管理：

- 首版订阅可默认归属到默认账本。
- 从账单创建订阅时继承该账单的 `ledgerId`。
- 订阅列表首版可按当前账本过滤；跨账本聚合可以后续增强。

酒店消费：

- `HotelStayDraft.targetLedgerId` 默认使用当前账本或默认账本。
- `HotelStayRecord.ledgerId` 与关联 `Transaction.ledgerId` 必须一致。
- 用户确认酒店消费前可以修改目标账本。

统计和展示端：

- iPhone / iPad / Mac 主 UI 支持当前账本 / 全部账本。
- Watch / Widget 默认展示默认账本或全部账本摘要，需在实现前明确口径。
- tvOS / visionOS 只读看板首版可以继续读取全部账本聚合快照，不做复杂切换。

### 10.4 多账本隐私与同步要求

- 多账本不改变本地优先原则。
- 账本名称可能包含私人信息，调试日志和截图 fixture 不应使用真实账本名。
- CloudKit 只同步结构化账本与交易字段，不上传原始截图、OCR 原文或调试记录。
- 归档账本不应删除交易；删除账本需要单独设计并要求先移动或确认处理账单。
- 冲突解决需要优先保护用户最近编辑的账本名称、默认账本选择和账单移动操作。

### 11.5 多语言账单识别语言包设计

App UI 多语言和账单识别多语言需要分层处理。`Localizable.strings` 只解决界面文案；普通记账解析链路还需要平台无关的识别语言包，承载不同语言账单中的金额、商户、日期、税费、支付渠道、退款 / 转账噪声和分类关键词。

设计目标：

- `AutoLedgerCore` 保持纯 Foundation，不依赖 SwiftUI、Vision、FoundationModels 或平台 OCR API。
- `LedgerTextInterpreterCore` 不直接硬编码单一语言关键词，而是通过语言包组合 `BillRelevanceGate`、`PaymentAmountExtractor`、`RuleMerchantExtractor`、`MerchantResolver` 和 `CategoryResolver` 所需的关键词 / 正则 / 排除规则。
- App 主链路继续负责 OCR、外部辅助识别开关、模型选择和 UI 提示；Core 负责稳定的本地规则草稿。
- 外部辅助识别 prompt 需要携带识别语言上下文，但金额、日期和是否正式入账仍以本地规则和用户确认优先。
- 新语言识别先从 `zh-Hans` / `zh-Hant` / `en` / `ja` 开始，后续 `ko` 作为候选。

建议模型：

```swift
struct LedgerRecognitionLanguagePack {
    let id: String                 // zh-Hans / zh-Hant / en / ja
    let schemaVersion: Int
    let packVersion: String
    let localeIdentifiers: [String]
    let billKeywords: [String]
    let paymentKeywords: [String]
    let amountLabels: [String]
    let totalLabels: [String]
    let discountLabels: [String]
    let taxLabels: [String]
    let dateLabels: [String]
    let merchantLabels: [String]
    let nonMerchantKeywords: [String]
    let categoryKeywordMap: [String: TransactionCategory]
    let provenance: LedgerRecognitionPackProvenance
}
```

可扩展性原则：

- 语言包必须是纯数据包，不允许包含可执行脚本、远程代码、动态表达式或运行时下载执行逻辑。
- 内置包、用户本地纠错覆盖包、社区审核包需要使用同一份 schema，通过 `schemaVersion` 和 `packVersion` 做兼容判断。
- 语言包应支持 fallback 链路，例如 `ja-JP → ja → en → builtin-default`，避免区域变体缺词时直接降级为识别失败。
- 每条关键词 / 标签规则应保留来源、权重、适用地区、示例类型和最后验证版本，便于回滚误加入的社区规则。
- 冲突处理按优先级合并：用户本地覆盖 > 内置热修复包 > 已审核社区包 > 内置基础包；金额字段和日期字段的高风险规则必须要求 golden case 通过后才能提升权重。
- 社区语言包建议以 JSON / YAML / Swift Package resource 的数据形式管理，进入主仓库前需要 code review、隐私检查、样例回归和许可说明。
- 语言包更新不应改变正式入账原则：低置信、多金额冲突、日期冲突或商户不确定时仍进入用户复核，不自动入账。

用户纠错与社区共享设计：

- 当用户在识别结果页修改商户、金额、日期、分类、支付方式、税费、折扣或账单语言时，可以提示“是否匿名共享这次纠错，用于改进语言包”。
- 共享必须默认关闭，并且只在用户主动勾选、可预览共享内容、明确确认后才发生；取消后不再上传本次纠错。
- 当前 `v1.6.1` 不实现上传通道。若未来启用，需要先更新隐私说明、Review Notes 和设置页开关，避免与“本地处理、零默认上传”的产品承诺冲突。
- 纠错共享 payload 应只包含最小必要数据：语言 / 地区 hint、语言包版本、解析字段类型、脱敏后的局部文本片段、用户修正后的标签类型、置信度变化和规则命中摘要。
- 不应共享完整截图、完整 PDF、完整 OCR 文本、完整邮箱正文、真实订单号、会员号、邮箱、手机号、银行卡号、身份证 / 护照号或精确住址。
- 金额、日期和商户名称是否共享需要额外谨慎：默认只共享格式模式和字段角色；如确需真实商户词条，应提供单独确认和人工审核入口。
- 用户纠错可以先生成本地 `UserRecognitionOverridePack`，立即改善同类账单识别；只有在用户 opt-in 后，才进入社区候选数据集。
- 社区候选数据进入正式语言包前需要去重、脱敏复核、误伤评估、跨语言回归和人工审核，不直接从用户提交自动生成线上规则。

统一处理流程：

```text
raw OCR / text
→ language detection or source locale hint
→ LedgerRecognitionLanguagePackSet
→ BillRelevanceGate
→ PaymentAmountExtractor
→ RuleMerchantExtractor / MerchantResolver
→ CategoryResolver
→ TransactionDraft / ImportedReceipt adapter
```

阶段拆分：

- Phase 0：只做设计与现状收敛。暂停 `detectMultipleReceipts` 多笔账单提示，避免重复金额行误触发；继续保留多商品小票 total 保护。
- Phase 1：新增 `LedgerRecognitionLanguagePack` 和 `LedgerRecognitionLanguagePackSet`，先把现有中文 / 英文关键词迁移为内置包，不改变识别结果。
- Phase 2：补 `ja` 识别包，覆盖日文常见字段：`合計`、`小計`、`支払金額`、`税込`、`税`、`領収書`、`レシート`、`店舗`、`加盟店`、`カード`、`割引` 等。
- Phase 3：让 App 主链路把 `Locale.autoupdatingCurrent`、OCR 语言 hint、截图 / 分享来源传入 Core，外部辅助识别 prompt 同步带上候选语言包 ID。
- Phase 4：建立多语言账单识别 golden cases，按语言维度覆盖金额、商户、分类、日期、非账单拦截和低置信复核。
- Phase 5：增加用户本地纠错覆盖包，让用户修正后的商户、分类、金额标签和语言选择优先影响本机后续识别。
- Phase 6：建立社区语言包候选流程，支持导出 / 导入脱敏纠错样例、人工审核、回归评分和数据包版本发布。
- Phase 7：评估 opt-in 纠错共享与社区协作入口；公共版本默认关闭，只有隐私说明、审核说明和服务端合规准备完成后才允许灰度。

当前不进入范围：

- 不实现多笔账单自动拆分。
- 不按语言包自动正式入账低置信结果。
- 不把语言包下载到云端或从云端动态更新。
- 不实现用户纠错上传、社区包自动分发或远程语言包热更新。
- 不要求外部模型覆盖本地规则缺失的金额；模型只做候选增强。
- 不在 `v1.6.1` 公共主链路开放邮箱 / Worker 自动化。

## 13. 回归与验收建议

A 阶段实现时建议至少覆盖：

- 文档样例 PDF 或 Demo Mode 可以完成导入、文本提取、解析、确认和入账。
- PDFKit 提取失败时有明确错误提示，不生成正式记录。
- 低置信和金额不平衡结果进入待确认。
- 用户拒绝草稿后不产生 `HotelStayRecord` 或 `Transaction`。
- 用户确认后产生一条 `HotelStayRecord`，并生成或关联一条普通支出流水。
- 删除草稿和删除正式记录路径可回归。
- `sourceType = .manualPDF` 能完整贯穿列表、详情、确认页和调试信息。
- 云模型路径开启时，发送前完成敏感字段脱敏。

多账本实现时建议至少覆盖：

- 旧账单在没有 `ledgerId` 时仍能显示在默认账本。
- 新账单写入明确 `ledgerId`。
- 切换当前账本不会改变账单数据。
- 将账单移动到其他账本后，列表、月报和同步字段一致。
- 归档账本后不删除历史交易。
- 备份导出 / 导入能保留账本与账单归属。
- CloudKit 同步不会丢失账本名称、默认账本和账单移动操作。

多语言实现时建议至少覆盖：

- 三语 `Localizable.strings` lint 通过。
- 日文 `Localizable.strings` lint 通过。
- 新功能关键路径没有明显硬编码中文 / 英文。
- 长文本在 iPhone / iPad / Mac 主要容器中不截断。
- App Intents / Shortcuts 展示文案在三语和日文下可读。
- 截图文案和 Review Notes 与实际提交平台一致。
- 日文截图、ASC 元数据和 Review Notes 经人工审校后再提交。
