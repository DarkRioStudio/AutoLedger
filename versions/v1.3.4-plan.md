## 4. 修复方向

### 4.1 金额提取重写

核心问题：`LedgerTextInterpreterCore` 当前采用"扫描文本找第一个金额样数字"策略，极易误取注册号、数量、价格而非合计金额。

修复策略：改为"合计行优先"策略：

```text
1. 扫描 TOTAL / Total / Grand Total / 合计 / 总金额 / Jumlah / Subtotal 等关键词行
2. 优先提取关键词行右侧/下方的金额
3. 若省略货币符号（RM 等），结合行上下文判断
4. 回退到"最后一个合理金额"策略
5. 输出 amountSource: "total_line" / "last_amount" / "fallback"
```

需要覆盖的合计关键词：
- 中文：合计、总计、总金额、实付、实收、应付
- 英文：TOTAL、Total、Grand Total、Subtotal、Amount Due、Total Due、TOTAL ROUNDED、Total Incl
- 马来文：Jumlah、Jumlah Besar
- 日文：合計
- 场景特色：Total Inclusive GST、Total incl GST、Total（RM）

排除信号：
- 营业执照号 / 注册号（XXXXX-X / XXXXX-D 格式）
- 单据编号（Doc No / Invoice No / Receipt# 开头的行）
- 数量（QTY 行右侧数字）
- 单价（PRICE 行右侧）

### 4.2 商户提取增强

核心问题：当前提取第一个"看起来像名字"的文本行，容易被 OCR 标题/页眉/页脚污染。

修复策略：

```text
商户候选链：
1. 优先从 OCR 文本顶部 1/4 区域提取（通常为商家名称区域）
2. 排除页眉特征：tan woon yann、cash sale、invoice、receipt、thank you
3. 排除纯大写公司注册号 / 税号行
4. 排除纯地址行（含 No./Jalan/Lot/Johor 关键词）
5. 结合已知平台关键词：`商户名称：`、`Merchant：`、`商户：`
6. 若未提取到合理商户名，标记 merchantMissing warning
```

商户黑名单（不应当作商户的常见 OCR 噪声）：
- "tan woon yann"、"tan chay yee" — OCR 页面底部水印/所有者名
- "Cash Sale"、"TAX INVOICE"、"INVOICE"、"RECEIPT" — 单据类型，非商户
- "Thank You"、"Please Come Again" — 页脚
- "GST Reg"、"GST ID" — 税号行

### 4.3 分类推断

核心问题：core 引擎将所有未知商户归为 "other"。

修复策略：

```text
1. 内置高频商户→分类映射表（从 ReceiptParser / SampleReceiptProvider 提取）
   - MR D.I.Y. / PERNIAGAAN ZHENG HUI → shopping
   - McDonald's / Gerbang Alaf Restaurants → dining
   - NTUC FAIRPRICE / WALMART → groceries
   - 滴滴出行 → transport
   - APPLE / Apple Services → digital
2. 匹配失败时检查 OCR 文本中的行业关键词
   - "RESTAURANT" / "Makan" / "McDonald's" → dining
   - "GROCERIES" / "Supermarket" / "FairPrice" → groceries
   - "TRANSPORT" / "TAXI" / "GRAB" → transport
3. 以上都不匹配 → other（不降级为错误）
```

### 4.4 TOTAL 行识别

核心问题：不同语言/地区的合计行格式差异大，当前规则覆盖面窄。

新增合计行格式覆盖：

```
TOTAL ROUNDED
Total Incl.GST:RM
Total Inclusive GST 6%
Total Sales （Inclusive of GST）：
Grand Total ：
Jumlah
Rounded Total （RM）：
Amount（RM）+ Tax（RM）并排结构
```

多币种支持：`RM`、`S$`、`HK$`、`NT$`、`Rp`、`₩`、`€`

## 7. 验收标准

- `LedgerTextInterpreterCore` 金额提取：
  - 合计行优先：对包含 `TOTAL/Total/合计/Grand Total/Jumlah/Subtotal` 的文本行能正确提取金额。
  - 排除注册号：营业执照/公司注册号（如 `860671-D`、`933109-X`）不会被误作金额。
  - 排除编号：单据编号、流水号不会被误作金额。
  - 回退策略：无合计行时至少尝试"最后一个合理金额"。
- `LedgerTextInterpreterCore` 商户提取：
  - "tan woon yann"、"Cash Sale"、"Thank You"、"INVOICE" 不会被当作商户。
  - 商户名优先从文本顶部 1/4 区域提取。
  - 平台支付截图支持 `商户名称：` / `商户：` / `Merchant：` 提取。
  - 无法提取商户名时输出 `merchantMissing` warning。
- `LedgerTextInterpreterCore` 分类推断：
  - 已知商户（MR D.I.Y.、McDonald's、NTUC FAIRPRICE 等）可正确分类。
  - 未知商户至少能按行业关键词推断。
  - 推断失败不降级（保留 other）。
- Golden Case：
  - core 引擎覆盖 ≥30 条。
  - core 引擎通过率 100%。
  - 覆盖面包含：中文支付截图、中文小票、英文小票、马来文小票、语音短句、非账单文本。
- `bash scripts/run_offline_regression.sh` 通过。
- `xcodebuild -workspace AutoLedger.xcworkspace -scheme AutoLedger -destination 'generic/platform=iOS' build` 通过。
- 批量 Markdown 报告可输出总样本数、可解析率、金额命中率、商户非空率、分类分布、失败 top 10。

## 8. Out of Scope

- 不新增 SQLite schema 或迁移。
- 不修改 `SmartReceiptParser`、`LedgerStore`、`Transaction` 等 App 层核心数据模型。
- 不修改 `BillRelevanceGate` 判断逻辑（除非发现误拦截）。
- 不开始 Apple Watch target 实现（v1.4 再做）。
- 不做 LLM-driven 规则增强。
- 不保证完全覆盖所有小票格式（目标是从当前 30% 提升到 70%+ 主流格式覆盖）。

## 9. 风险与应对

| 风险 | 应对 |
|------|------|
| 合计行关键词过多导致维护成本高 | 关键词表设计为可配置 `[String]`，独立于核心逻辑 |
| 商户黑名单误杀真实商户 | 黑名单只包含明确的非商户行特征；低置信商户走 needsReview |
| core 引擎修复导致 receiptParser 引擎倒退 | 每种修复先在 Golden Case 加断言再改代码 |
| 马来文/地区小票覆盖不足 | 第一阶段优先覆盖 batch first10 报告中的故障样本 |
| 金额提取从"取第一个"改为"合计优先"可能引入新遗漏 | 保留回退策略 + amountSource 调试字段，便于排查 |

## 10. 回滚方案

- 保留 v1.3.3 的 core 引擎实现目录（`AutoLedgerCore/Services/LedgerTextInterpreterCore.swift` 可通过 git revert 恢复）。
- Golden Case 新增样本可按文件独立回滚。
- 批量 Markdown 报告工具不影响 App 主流程。
- 若 Phase 4 receiptParser→core 迁移出现阻塞，可暂缓迁移，只保留新增 core case。
