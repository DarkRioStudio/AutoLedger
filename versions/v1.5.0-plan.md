# v1.5.0 开发线规划

更新日期：2026-06-02
文档状态：当前开发线，随开发进程持续校正
内部开发线：v1.5.0 / v1.5.x
App Store 对外版本：v1.4.0
承接版本：App Store v1.3.0 / 内部 v1.4.0 发布基准
关联设计：`versions/v1.4.0-plan.md`、`versions/v1.4.0-RELEASE(draft).md`、`AutoLedger_Watch_Design.md`

## 1. 版本定位

v1.5.0 是 AutoLedger 在内部 v1.4.0（对外 App Store v1.3.0）已过审发布之后，面向下一轮 App Store v1.4.0 的开发线。

当前项目版本已切换到：

| 项目 | 当前值 |
|------|--------|
| 内部开发线 | v1.5.0 / v1.5.x |
| App Store 对外版本 | v1.4.0 |
| 承接基准 | `v1.4.0` tag（App Store v1.3.0 已发布） |

本轮不只是继续补 OCR 规则，而是把 AutoLedger 从“手机上的截图记账工具”推进到“全平台本地优先账单工作流”：

1. Apple Watch 第一屏改为更有用的“今日支出”摘要。
2. Watch 向左滑第二屏显示当前账本关联的最近支出。
3. 设计并实现表盘小组件适配，让今日消费信息能在手表表盘上被快速查看。
4. 增加 iPad 端，把 iPad 定位为统计分析、批量导入、批量识别、数据清洗和多账本管理的主工作台。
5. 解决基础多端数据同步问题，让 iPhone、iPad、Apple Watch、后续 Mac Catalyst 和只读展示端不再依赖各自临时口径。
6. iPad 端完善后，使用 Mac Catalyst 将工作台推进到 Mac 端，承载拖拽导入、CSV / JSON 导入导出、键盘快捷键、菜单栏和更大表格编辑区域。
7. 规划 tvOS 只读大屏看板，面向家庭场景展示本月支出、分类占比、最近趋势和年度 / 月度摘要。
8. 规划 visionOS 展示版本，面向空间看板、漂浮分类卡片、年度消费时间线墙和最近账单悬浮列表。
9. 继续优化识别链路，拓展更多真实账单场景。

v1.5.x 是内部开发线；App Store 对外发布版本是 v1.4.0。

开发过程中允许使用 v1.5.1、v1.5.2、v1.5.3 等内部阶段号拆分任务、生成 TestFlight 构建和记录回归节点。用户最终在 App Store 看到的是：

## 2. 产品目标

### 2.1 核心目标

- Watch 端从“可操作入口”升级为“随手看今日支出”：
  - 第一屏显示今日支出总金额。
  - 显示今日支出笔数。
  - 显示最近一笔商户。
  - 左滑第二屏显示当前账本关联的最近支出列表。
  - 保留快速记账和最近账单入口。

- 表盘小组件完成第一版适配：
  - 在表盘上显示今日支出金额或今日支出笔数。
  - 点击小组件进入 Watch App 今日支出页。
  - 支持隐私隐藏、空状态和数据过期提示。

- iPad 端完成第一版产品框架：
  - 统计分析。
  - 数据批量导入。
  - 批量识别。
  - 数据清洗整理。
  - 结构化成账单。
  - 多账本管理。

- 基础多端数据同步成为 v1.5.0 必须解决的底座问题：
  - 明确 iPhone / iPad / Mac Catalyst 的账本同步策略。
  - 明确 Apple Watch 写入、今日支出、最近支出与主账本之间的最终一致性边界。
  - 明确 Widget、tvOS、visionOS 等只读展示端读取的是本机快照、iCloud 同步数据还是受控发布快照。
  - 明确冲突处理、重复写入、防丢失和离线恢复策略。
  - 保持 local-first，不引入服务端账户系统作为 v1.5.0 的前置条件。

- Mac Catalyst 端作为 iPad 工作台稳定后的生产力延伸：
  - 支持 Finder 拖拽截图 / 文件导入。
  - 支持 CSV / JSON 导入导出。
  - 支持键盘快捷键和基础菜单栏。
  - 支持更大的表格 / 列表编辑区域。
  - 支持批量选择、批量修正和重复账单检查。

- tvOS 端定位为只读家庭大屏看板：
  - 本月支出总览。
  - 分类占比。
  - 最近消费趋势。
  - 年度 / 月度摘要。
  - 家庭大屏展示模式。

- visionOS 端定位为空间展示版本：
  - 月度支出空间看板。
  - 分类支出卡片漂浮展示。
  - 年度消费时间线墙。
  - 最近账单悬浮列表。

- 截图与发布资产管线覆盖 iPad：
  - 当前 App Store 截图管线只覆盖 iPhone 与 Apple Watch，不生成 iPad 截图。
  - v1.5.0 需要把 iPad 端纳入截图管线，覆盖关键页面与 App Store 发布资产。
  - iPad 首版 UI 需要从设计阶段就考虑截图可展示性。
  - iPhone、Watch、iPad 三端截图口径统一管理。

- 识别链路继续拓展：
  - 覆盖更多支付、订单、票据、订阅和跨场景账单。
  - 让“识别 → 复核 → 入账 → 清洗 → 统计”的链路更稳定。

### 2.2 非目标

v1.5.0 第一版规划不把 AutoLedger 扩展成完整财务系统。

本轮暂不包含：

- 服务端账户系统。
- 多人协作账本。
- 银行级资产负债管理。
- 预算、投资、贷款、发票报销等完整财务模块。
- 不经用户确认的历史账单大规模自动改写。
- 付费能力边界设计。
- Mac 原生 App 重写；Mac 首版优先走 Catalyst 评估。
- tvOS / visionOS 的编辑、导入、清洗或写入账本能力；两者首版只读展示。

## 3. Apple Watch 主线

### 3.1 第一屏：今日支出

Watch App 打开后的第一屏改为“今日支出”，让用户抬腕就能确认当天消费状态。

第一屏信息结构：

| 信息 | 展示要求 | 说明 |
|------|----------|------|
| 今日支出总金额 | 最大视觉层级 | 使用当前账本默认币种；无支出时显示 0 或空状态文案 |
| 今日支出笔数 | 次级指标 | 显示 `共 N 笔`，便于判断今天消费频率 |
| 最近一笔商户 | 次级摘要 | 优先显示商户名；无商户时显示分类或账单来源 |
| 同步状态 | 轻量提示 | 仅在数据过期、同步失败、等待 iPhone 时显示 |
| 操作入口 | 底部或卡片按钮 | 快速记账、语音记账、最近账单 |

基础状态：

- 空状态：今天还没有支出，保留快速记账入口。
- 加载状态：本地数据读取或等待 iPhone 回传时显示轻量占位。
- 离线状态：显示上次同步时间，允许继续本地暂存记账。
- 隐私状态：用户开启隐私隐藏时，金额显示为占位符，点按后进入 App 可查看。

执行状态（2026-06-01 / GOAL-1511）：首屏已切换为今日支出摘要。当前展示今日总金额、今日笔数、最近展示名、更新时间、语音记账和快速记账入口；隐私隐藏开关尚未实现。

### 3.2 左滑第二屏：账本关联最近支出

Watch 今日支出页向左滑进入第二屏，显示当前账本关联的最近支出。

第二屏信息结构：

| 信息 | 展示要求 | 说明 |
|------|----------|------|
| 当前账本 | 顶部轻量标识 | 显示默认账本或当前选中账本名称 |
| 最近支出列表 | 主体内容 | 展示最近 3～5 笔支出，按交易时间倒序 |
| 单笔摘要 | 金额 + 商户 / 分类 | 空商户时用分类兜底 |
| 时间提示 | 今天 / 昨天 / 日期 | Watch 小屏上避免完整时间过长 |
| 详情入口 | 点按单笔进入详情 | 第一版只读详情，复杂编辑留给 iPhone / iPad |

数据口径：

- 只展示当前账本关联的支出记录。
- 默认使用用户当前默认账本；多账本上线后，可跟随 iPhone / iPad 最近使用账本。
- 如果账本没有最近支出，显示空状态并保留快速记账入口。
- Watch 上不做账本切换的复杂管理，最多提供轻量账本名称提示。

交互原则：

- 第一屏负责“今天花了多少”，第二屏负责“最近花在哪里”。
- 左右滑动不应隐藏核心操作，快速记账入口仍需容易到达。
- 第二屏列表不承载批量清洗、分类学习、账本移动等重操作。

执行状态（2026-06-01 / GOAL-1511）：为避免首屏改造后丢失旧列表能力，最近 5 笔支出已保留为 Watch 左滑第二页。

执行状态（2026-06-01 / GOAL-1512）：第二页已补齐当前账本提示、今天 / 昨天 / 日期短时间文案和单笔只读详情。详情页展示金额、商户、分类、来源、时间和备注，不提供编辑、删除或账本移动。

### 3.3 默认账本与今日支出口径（GOAL-1501）

今日支出应按用户本地日历日统计，不按 UTC 自然日统计。该口径同时服务 Watch 首屏、Watch 表盘小组件、iPad 总览、Mac Catalyst 表格摘要、tvOS 大屏看板和 visionOS 空间看板。

#### 3.3.1 默认账本口径

当前工程还没有 `Ledger` 模型，也没有 `Transaction.ledgerId`。在多账本上线前，系统使用一个虚拟默认账本承载所有正式账单：

| 项目 | v1.5.0 当前口径 | 多账本上线后的迁移口径 |
|------|------------------|------------------------|
| 默认账本 ID | `default-local-ledger`（文档与迁移约定，不要求当前代码立即新增字段） | 旧账单迁移时统一写入该默认账本，后续可重命名但 ID 保持稳定 |
| 默认账本显示名 | `本地账本` / `Local Ledger` | 用户可改名；Watch / Widget 无复杂切换时继续跟随默认账本 |
| 当前账本 | iPad / Mac 可有显式选中账本；未选择时回退默认账本 | 选中账本用于工作台筛选，默认账本用于轻量展示和新账单默认归属 |
| 全部账本 | 当前等同于默认账本 | 多账本后作为聚合统计范围，必须与单账本统计明确区分 |

默认规则：

- 当前所有 `store.transactions` 中的活跃账单都视为属于默认账本。
- `deletedTransactions` 不参与默认账本活跃统计，但备份和最近删除视图仍保留。
- Raw Input、Candidate、Rejected 等候选状态不属于正式账本，确认入账前不参与默认账本统计。
- Watch / Widget / tvOS / visionOS 首版默认展示默认账本，不跟随 iPad / Mac 的临时筛选状态。
- iPad / Mac 工作台可以显示当前选中账本；若没有显式选择，则显示默认账本。

#### 3.3.2 今日支出统计范围

今日支出只统计“正式、活跃、支出型”的账单：

| 项目 | 是否计入今日支出 | 说明 |
|------|------------------|------|
| 正式账单 `Transaction` | 是 | 当前模型里的账单均视为支出账单，前提是金额大于 0 |
| `amount > 0` | 是 | 当前 App 只保存支出；未来支持收入 / 退款后需新增类型字段 |
| `amount == 0` 或负数 | 否 | 视为异常或未来退款 / 调整，不进入今日支出 |
| 已删除账单 | 否 | 软删除后从活跃统计中排除 |
| 候选账单 | 否 | 用户确认前不污染统计 |
| 被标记疑似重复但仍为正式账单 | 是 | 只提示风险，不静默排除；用户确认删除 / 合并后再变化 |
| 订阅元数据 | 否 | 只有已经生成正式 `Transaction` 的订阅扣费才计入 |
| 手动 / Watch / 语音 / 快捷指令 / Share Extension 入账 | 是 | 只要进入正式账本并满足日期与金额条件，来源不影响统计 |

#### 3.3.3 日期边界

今日支出使用用户当前本地日历日：

- 日区间为 `[localStartOfDay, nextLocalStartOfDay)`。
- 日历使用用户设备当前 calendar / timezone；不能使用 UTC 自然日。
- 账单以 `occurredAt` 为准，不以导入时间、识别时间或备份时间为准。
- 未来如果保存 `createdAt` / `updatedAt` 到模型层，仍只作为排序兜底，不改变今日归属。
- 夏令时或时区变化时，以设备当前本地 calendar 算出的日期区间为准。

#### 3.3.4 最近支出口径

Watch 第二屏、iPad 总览和展示平台的“最近支出”使用同一排序：

1. 仅取当前统计范围内的正式活跃账单。
2. 按 `occurredAt` 倒序。
3. 若未来模型提供 `createdAt` / `updatedAt`，同一 `occurredAt` 下再按创建 / 更新时间倒序。
4. 商户为空时用分类标题兜底；分类也不可读时显示“待确认”。

#### 3.3.5 币种与金额

当前 `Transaction` 没有币种字段，`AppFormatters.currency` 固定按 CNY / `¥` 展示。因此 v1.5.0 今日支出暂定：

- 所有正式账单金额按当前默认币种显示。
- 多币种 OCR 可以进入备注或候选 warning，但确认入账前必须让用户明确最终金额。
- 未做汇率换算前，不在总览中混合显示不同币种金额。
- 后续若新增 `currencyCode` / `originalAmount` / `exchangeRate`，默认账本统计需明确“本币合计”和“原币展示”的关系。

#### 3.3.6 测试用例设计

GOAL-1510 实现今日支出数据服务时，至少补齐以下离线用例：

| Case | 输入 | 期望 |
|------|------|------|
| today_active_expense_included | 今天 2 笔正金额正式账单 | 总金额为两笔合计，笔数为 2 |
| yesterday_expense_excluded | 昨天 1 笔正金额账单 | 今日支出不包含该笔 |
| deleted_expense_excluded | 今天 1 笔已删除账单 | 今日支出不包含该笔 |
| candidate_excluded | 今天 1 条候选账单 | 今日支出不包含该候选 |

#### 3.3.7 今日支出数据服务（GOAL-1510）

GOAL-1510 已在 `AutoLedgerCore` 中新增 `TodaySpendingSummary`，作为 Watch 首屏、Watch 表盘小组件、iPad 总览、Mac Catalyst 表格摘要、tvOS 和 visionOS 展示平台的共同数据口径。

服务输出：

| 字段 | 说明 |
|------|------|
| `ledgerID` | 当前为 `default-local-ledger` |
| `ledgerName` | 当前为 `本地账本` |
| `dayInterval` | 按传入 calendar 计算的本地日区间 |
| `totalExpense` | 今日正金额正式账单合计 |
| `transactionCount` | 今日正金额正式账单笔数 |
| `recentTransaction` | 今日最近一笔正式支出 |
| `recentDisplayName` | 最近一笔展示名，优先商户，商户为空时回退分类 / 来源 |
| `isEmpty` | 今日无有效支出时为 true |

服务输入契约：

- 输入数组必须是“活跃正式账单”。当前由 `LedgerStore.transactions` 提供，不传入 `deletedTransactions`。
- 候选账单、raw input、rejected、debug events 不进入该服务输入。
- 当前没有 `ledgerId` 字段，因此所有输入账单暂视为默认账本。
- 多账本上线后，调用方负责按默认账本、当前账本或全部账本过滤后再调用 summary。

过滤规则：

- 只统计 `amount > 0`。
- 只统计 `occurredAt` 落在 `[localStartOfDay, nextLocalStartOfDay)` 的账单。
- 日期区间由注入的 `Calendar` 计算；默认使用设备当前 calendar。
- 最近支出按 `occurredAt` 倒序；当前模型没有 `createdAt` / `updatedAt`，后续新增字段后可补充二级排序。

App 层接入：

- `LedgerStore.todaySpendingSummary` 现在返回 `TodaySpendingSummary.build(from: transactions, referenceDate: .now)`。
- 本轮不改 Watch UI、不改 Widget、不改 WatchConnectivity payload；GOAL-1511 / GOAL-1520 后续复用该 summary。

### 3.4 Watch 交互原则

- Watch 上只做轻量查看和快速记录，不做复杂账单清洗。
- 今日支出页优先保证一眼读懂，不堆图表。
- 编辑、批量操作、数据清洗统一引导到 iPhone / iPad。
- VoiceOver、大字号、减动、增强对比度必须在主路径可用。

## 4. 表盘小组件适配

### 4.1 第一版范围

表盘小组件先围绕“今日支出”做最小可用集：

| Widget Family | 第一版内容 | 备注 |
|----------------|------------|------|
| Accessory Inline | `今日支出 ¥88` | 适合文字型表盘区域 |
| Accessory Circular | 金额缩写 | 圆形表盘区域只显示金额，使用支出程度色彩 |
| Accessory Rectangular | 今日金额 + 最近商户 / 状态 | 内容左对齐，避免表盘中部显得漂浮 |
| Accessory Corner | 短金额 + 线性彩色进度条 | 参考天气组件，金额显示在角落主读数位置，隐藏 current / min / max 标签，用位置点表达支出程度 |

执行状态：

## 5. iPad 主线

### 5.1 产品定位

iPad 端不是简单放大 iPhone UI，而是 AutoLedger 的“账单整理工作台”。

用户在 iPhone / Watch 上负责快速记录，在 iPad 上完成更重的整理工作：

1. 批量导入截图、图片、文件或文本。
2. 批量识别候选账单。
3. 复核、清洗、合并、去重和分类。
4. 结构化为正式账单。
5. 按账本、月份、分类、商户做统计分析。

### 5.2 信息架构

建议第一版采用 iPad 常见的三段式结构：

| 区域 | 内容 | 目标 |
|------|------|------|
| 左侧边栏 | 账本、月份、导入箱、清洗任务、统计入口 | 快速切换工作上下文 |
| 中间列表 / 表格 | 账单、候选记录、批量识别结果 | 支持批量选择和排序筛选 |
| 右侧详情 / 检查器 | 识别字段、原图预览、清洗建议、账单详情 | 让复核和修正不离开当前页面 |

### 5.3 统计分析

iPad 统计分析优先服务“看懂钱花到哪里”：

- 月度支出总览：总金额、笔数、日均支出、环比变化。
- 分类分析：分类金额、占比、趋势变化。
- 商户分析：Top 商户、重复消费、订阅类消费。
- 账本分析：个人、家庭、旅行、工作等账本维度的对比。
- 时间分析：日历热力、周内分布、月内峰值。
- 异常提示：大额、重复、疑似误识别、分类异常。

第一版不追求复杂图表堆叠，优先保证筛选、钻取和数据可信。

### 5.4 数据批量导入

第一版导入场景：

- 从系统照片选择多张账单截图。
- 从 Files 拖入图片、PDF 或文本文件。
- 从剪贴板粘贴多条账单文本。
- 从分享入口进入 AutoLedger 导入箱。

导入后先进入“候选区”，不直接写入正式账本。

候选区字段：

- 来源类型。
- 原始文件名或截图来源。
- 识别状态。
- 识别置信度。
- 候选金额、商户、时间、分类。
- 是否疑似重复。
- 是否需要人工复核。

### 5.5 批量识别

批量识别采用队列模型：

1. 导入文件进入队列。
2. 逐项 OCR / 文本解析。
3. 生成候选账单。
4. 标记置信度和异常原因。
5. 用户批量确认或逐条修正。

队列需要支持：

- 暂停 / 继续。
- 失败重试。
- 识别结果重新解析。
- 按状态筛选：待识别、待复核、可入账、失败、疑似重复。
- 大批量导入时不阻塞 UI。

### 5.6 数据清洗整理

数据清洗是 iPad 端的重点能力。

第一版清洗项：

- 商户统一：把不同写法归并为同一商户。
- 分类修正：批量修改同类商户或同类记录的分类。
- 重复检测：按金额、时间、商户、来源相似度提示疑似重复。
- 字段补全：时间、商户、分类、备注缺失时提示补齐。
- 金额异常：识别金额与文本上下文冲突时标记。
- 来源整理：记录账单来自截图、文本、手动、Watch、快捷指令等路径。

所有批量清洗动作都必须有确认步骤，并尽量提供撤销或可回滚路径。

### 5.7 结构化成账单

候选记录进入正式账本前，应经过结构化确认：

| 阶段 | 状态 | 说明 |
|------|------|------|
| Raw Input | 原始输入 | 图片、PDF、文本、剪贴板内容 |
| Candidate | 候选账单 | OCR / 文本解析后的结构化草稿 |
| Reviewed | 已复核 | 用户确认字段正确 |
| Transaction | 正式账单 | 写入账本并进入统计 |
| Rejected | 已忽略 | 非账单或用户放弃 |

第一版可先在 UI 和存储层建立清晰状态，后续再逐步增强自动化。

### 5.7.1 候选账单状态模型（GOAL-1502）

候选账单模型是 iPad / Mac 批量导入、批量识别、数据清洗和重复检查的共同基础。它不替代当前 `Transaction`，也不能在用户确认前污染正式账本统计。

#### 5.7.1.1 状态流

第一版状态流保持线性、可追溯、可回滚：

```text
Raw Input -> Candidate -> Reviewed -> Transaction
Raw Input -> Rejected
Candidate -> Rejected
Candidate -> Candidate (retry / reparse)
Reviewed -> Candidate (commit failed or user reopens review)
```

| 状态 | 含义 | 是否进入正式账本 | 是否进入统计 | 典型入口 |
|------|------|------------------|--------------|----------|
| `rawInput` | 已导入原始图片、PDF、文本、剪贴板内容或分享内容，尚未产生可信结构化草稿 | 否 | 否 | iPad / Mac 批量导入、剪贴板、Share Extension、快捷指令 |
| `candidate` | OCR / 文本解析后得到结构化草稿，但字段仍需用户复核 | 否 | 否 | 批量识别、重新解析、低置信解析 |
| `reviewed` | 用户已确认字段，可准备写入指定账本 | 否 | 否 | 单条确认、批量确认后的暂存阶段 |
| `transaction` | 已成功写入正式 `Transaction`，进入活跃账本 | 是 | 是 | 保存成功后的目标状态 |
| `rejected` | 用户忽略、非账单、识别失败且不再处理 | 否 | 否 | 非账单图片、重复项、用户放弃 |

状态约束：

- 只有 `transaction` 状态能写入当前 `transactions` 表并进入 Watch / Widget / iPad / Mac / tvOS / visionOS 统计。
- `rawInput`、`candidate`、`reviewed`、`rejected` 均不计入今日支出、月报或 Top 商户。
- `reviewed` 是入账前的事务性暂存状态；如果提交失败，应保留用户修正字段并回到 `candidate` 或继续显示为待提交。
- 重新识别不创建正式账单，只更新候选记录的解析版本、置信度、warning 和失败原因。
- `rejected` 仍应保留最小审计信息，便于撤销忽略、排查批量导入问题和避免重复导入。

#### 5.7.1.2 最小字段草案

GOAL-1502 只定义字段契约，不要求本轮写 SQLite schema。后续 GOAL-1503 再决定字段落库、索引、迁移和 BackupBundle 版本。

| 字段组 | 字段 | 说明 |
|--------|------|------|
| 身份与批次 | `id`、`batchId`、`createdAt`、`updatedAt` | 候选记录唯一标识、导入批次和排序追踪 |
| 原始输入 | `sourceKind`、`originalFileName`、`originalUTType`、`inputHash`、`rawText`、`thumbnailRef`、`fileRef` | 记录来源、文件类型、去重 hash、OCR / 文本结果和本地文件引用 |
| 解析草稿 | `merchant`、`amount`、`occurredAt`、`category`、`source`、`note` | 对齐当前 `Transaction` 的核心字段 |
| 扩展草稿 | `currencyCode`、`originalAmount`、`ledgerId` | 当前可为空；为多币种和多账本预留 |
| 状态与质量 | `state`、`confidence`、`needsReview`、`warnings`、`failureReason` | 驱动候选列表筛选、复核优先级和失败重试 |
| 重复提示 | `duplicateGroupId`、`duplicateScore`、`duplicateReason`、`possibleDuplicateTransactionId` | 只提示，不自动删除或静默跳过 |
| 复核与入账 | `reviewedAt`、`targetLedgerId`、`convertedTransactionId` | 记录确认时间、目标账本和成功转入的正式账单 ID |
| 隐私与清理 | `rawContentPurgedAt`、`retentionPolicy` | 允许用户清理原图 / 原文，同时保留必要状态 |

隐私约束：

- 原始图片、OCR 全文、PDF 文本和支付截图可能包含个人财务信息，不能进入公开 fixtures、公开 issue 或示例仓库数据。
- Debug / backup / export 必须区分“正式账单字段”和“原始敏感输入”；后续备份升级应明确是否包含原始输入。
- 如果用户清理原始输入，候选记录可以保留安全摘要、状态和已确认字段，但不能继续暴露原图或 OCR 全文。

#### 5.7.1.3 失败原因

第一版失败原因建议使用稳定枚举，避免 UI 和回归脚本依赖任意字符串：

| Reason | 场景 | 默认处理 |
|--------|------|----------|
| `emptyInput` | 文件或文本为空 | 标记失败，允许删除 |
| `ocrFailed` | 图片 OCR 失败 | 允许重试或手动输入 |
| `nonBillImage` | 缺少账单信号 | 标记为已忽略建议 |
| `missingAmount` | 没有可信金额 | 进入候选，强制复核 |
| `missingMerchant` | 没有可信商户 | 进入候选，商户字段待补全 |
| `missingDate` | 没有可信日期 | 进入候选，默认不自动入账 |
| `lowConfidence` | 解析置信度低 | 进入候选并置 `needsReview = true` |
| `multipleReceipts` | 一张图可能包含多笔账单 | 拆分前不写入正式账本 |
| `duplicateSuspected` | 疑似与已有账单或候选重复 | 提示用户确认，不自动删除 |
| `unsupportedFileType` | 不支持的文件类型 | 标记失败并提示支持范围 |
| `parseFailed` | 解析器异常或无草稿 | 保留 raw input，允许重试 |
| `userRejected` | 用户主动忽略 | 转为 `rejected` |
| `permissionDenied` | 文件 / 照片权限不足 | 停留 raw input 或失败状态 |

#### 5.7.1.4 置信度与复核策略

当前工程已有 `ImportedReceipt.confidence`、`InterpretResult.confidence`、`needsReview` 和 `warnings` 等概念。候选模型应收敛这些信号，统一驱动 iPad / Mac 复核工作台：

| 置信度 | 建议阈值 | 默认行为 |
|--------|----------|----------|
| High | `confidence >= 0.80` | 可以预选为“可确认”，但批量入账前仍需用户确认 |
| Medium | `0.50 <= confidence < 0.80` | 进入候选区，要求复核关键字段 |
| Low | `confidence < 0.50` | 保留候选或 raw input，显示失败原因和重试入口 |

规则：

- 批量导入场景不做无确认自动入账，即使置信度高也只进入可确认队列。
- `needsReview = true` 时，UI 必须突出显示待确认字段。
- 多币种、疑似重复、缺日期、缺商户、金额冲突等 warning 优先级高于单纯高置信度。
- 用户手动修正后的字段应覆盖解析草稿，并记录 `reviewedAt`。

#### 5.7.1.5 重复提示策略

重复检测只负责提示，不负责静默删除。

候选账单应同时与两类对象比较：

1. 活跃正式账单：避免用户把同一截图再次入账。
2. 同批或历史候选账单：避免批量导入重复图片、重复 PDF 页或同一文本多次进入队列。

第一版比较因子：

- `inputHash` 完全一致。
- 金额相同或非常接近。
- `occurredAt` 在同一天或短时间窗口内。
- 商户相同、别名相同或文本相似。
- OCR / raw text 相似度高。
- 来源文件名或图片元数据高度相似。

重复提示落地规则：

- 疑似重复候选设置 `duplicateScore`、`duplicateReason` 和 `needsReview = true`。
- 不自动把候选转成 `rejected`，除非用户确认忽略。
- 不自动删除已有正式账单。
- 如果用户确认仍然入账，该正式账单照常进入统计，后续由数据清洗 / 合并能力处理。

#### 5.7.1.6 后续落库与备份边界

后续 GOAL-1503 评估 schema 时，建议至少考虑：

- `import_batches`：批量导入会话、来源、创建时间、完成状态。
- `raw_inputs`：原始文件 / 文本引用、hash、OCR 文本、权限和清理状态。
- `candidate_transactions`：候选字段、状态、置信度、失败原因、重复提示和目标账本。
- `candidate_events`：重试、修正、忽略、确认、入账失败、入账成功等审计事件。

BackupBundle 需要谨慎升级：

- `schemaVersion = 1` 当前只覆盖正式账单与删除状态，不应强行塞入候选队列。
- 如果 v1.5.x 要备份候选区，应升级到 schema v2，并让用户知道是否包含原始敏感输入。
- 导出 CSV 默认只导出正式账单；JSON backup 可以选择是否包含候选队列。

#### 5.7.1.7 测试用例设计

后续实现候选模型、队列和持久化时，至少补齐：

| Case | 输入 | 期望 |
|------|------|------|
| raw_text_creates_raw_input | 粘贴一段账单文本 | 生成 `rawInput`，不进入统计 |
| ocr_failure_preserves_raw | OCR 失败图片 | 保留 raw input、失败原因为 `ocrFailed` |
| non_bill_rejected | 非账单图片 | 可转 `rejected`，不进入正式账本 |
| missing_amount_candidate | 缺金额文本 | 生成 candidate，`needsReview = true` |
| high_confidence_candidate_not_auto_saved | 高置信账单 | 进入可确认候选，不自动入账 |
| duplicate_suspected_not_deleted | 与已有账单相似 | 标记重复提示，不删除候选或正式账单 |
| reviewed_then_transaction | 用户确认字段并保存 | 先 reviewed，再生成正式 `Transaction` |
| rejected_excluded_from_stats | 用户忽略候选 | 不进入今日 / 月度统计 |
| purge_raw_keeps_summary | 用户清理原始输入 | 原图 / 原文不可见，状态摘要保留 |

### 5.8 多账本管理

多账本用于把不同生活场景分开：

- 个人账本。
- 家庭账本。
- 旅行账本。
- 工作 / 报销账本。
- 临时项目账本。

第一版能力：

- 创建、重命名、归档账本。
- 设置默认账本。
- 导入时选择目标账本。
- 账单可在账本间移动。
- 统计分析可按单账本或全部账本查看。

暂不做多人协作和服务端同步。

### 5.9 SQLite / BackupBundle 迁移方案（GOAL-1503）

GOAL-1503 只输出 schema 缺口与迁移方案，不在本轮修改数据库、模型或备份代码。核心原则是：现有正式账单继续可读可写；旧数据自动归入默认账本；候选区独立于正式账单；备份恢复必须兼容现有 schema v1。

#### 5.9.1 当前 schema 事实

当前 `SQLiteTransactionStore` 初始化时使用 `CREATE TABLE IF NOT EXISTS` 加少量列存在性迁移，没有集中式 schema version 表。

| 对象 | 当前状态 | 缺口 |
|------|----------|------|
| `Transaction` | `id`、`merchant`、`amount`、`occurredAt`、`category`、`source`、`note` | 无 `ledgerId`、`currencyCode`、`transactionType`、`createdAt`、`updatedAt` 模型字段 |
| `transactions` 表 | `id`、`merchant`、`amount`、`occurred_at`、`category`、`source`、`note`、`created_at`、`updated_at`、`deleted_at` | 无 `ledger_id`、`currency_code`、`transaction_type`、候选来源、重复组或清洗历史 |
| `debug_events` 表 | 保存 OCR / LLM 调试事件、raw text、解析结果、交易 ID、LLM metadata | 不是候选队列；不能直接承担 iPad / Mac 批量复核状态 |
| `subscriptions` 表 | 保存订阅识别结果 | 与多账本、候选入账、交易归属尚未关联 |
| `category_corrections` 表 | merchant -> 内置 `TransactionCategory` | 不能表达自定义分类的持久化关系和多账本作用域 |
| `merchant_aliases` 表 | original -> alias | 可复用，但清洗动作历史尚未记录 |
| 自定义分类 / 来源 | 主要在 UserDefaults，BackupBundle 会导出数组 | 不在 SQLite，未来 iPad / Mac / 多平台工作台需要统一持久化 |
| `BackupBundle` | `schemaVersion = 1`，validator 只接受 1 | 不覆盖 ledgers、candidate queue、raw inputs、cleaning actions、transaction v2 fields |

#### 5.9.2 迁移总原则

- 迁移必须是 additive first：先加表、加可空列或有默认值的列，不重建现有正式账单表。
- 旧正式账单迁移后全部写入 `default-local-ledger`，不改变 ID、金额、商户、日期、分类、来源和备注。
- 候选账单不得复用 `transactions` 表表达未确认状态，避免污染今日支出、月报、Watch、Widget 和展示平台。
- BackupBundle v1 必须继续可导入；导入 v1 时自动映射到默认账本。
- BackupBundle v2 导出前必须明确是否包含候选区和原始敏感输入。
- Xcode Cloud / App Store 发布链不依赖本地数据库 fixture；schema 迁移不得修改 Bundle ID、signing、entitlements、App Group 或 iCloud Container。

### 5.10 基础多端数据同步

v1.5.0 的全平台路线不能只扩展 UI。iPad、Mac Catalyst、Apple Watch、Widget、tvOS 和 visionOS 都需要看到同一套账本事实，否则会出现“手机上已入账、iPad / Watch / 大屏仍显示旧数据”的割裂体验。

当前同步现状：

| 路径 | 当前能力 | 缺口 |
|------|----------|------|
| iPhone / iPad | 同一个 iOS App target 可运行在不同设备 | 不同设备之间没有结构化实时同步；iCloud Drive 单文件备份不等于多端同步 |
| Apple Watch | 通过 WatchConnectivity 同步最近账单、分类、今日支出摘要；Watch 离线写入 pending 队列 | 不是完整账本复制；依赖 iPhone 可达或后台传输，不能承诺实时 |
| Widget | 读取本机 App Group SQLite | 只能反映当前设备本机数据，不代表其他设备最新状态 |
| Mac Catalyst | 规划复用 iPad 工作台 | 若没有 iCloud / CloudKit / 受控备份同步，Mac 与 iPhone / iPad 数据可能分叉 |
| tvOS / visionOS | 规划只读展示 | 展示端必须读取稳定快照，不能各自发明统计口径 |
| JSON / iCloud Drive 备份 | 支持手动迁移和轻量恢复 | 适合备份恢复，不适合作为无感多端协作同步 |

v1.5.0 至少需要解决的基础同步问题：

1. 明确主账本数据源：正式账单、删除账单、订阅、自定义分类 / 来源、商户别名、分类修正、多账本元数据和候选队列分别如何同步。
2. 明确同步介质：继续扩展 iCloud Drive BackupBundle、引入 CloudKit private database，或采用分阶段策略。
3. 明确写入端边界：iPhone / iPad / Mac 可写；Apple Watch 可离线暂存并回传；tvOS / visionOS 首版只读。
4. 明确冲突策略：同一账单在多端编辑、删除、恢复、批量清洗时如何判定最终状态。
5. 明确重复写入防护：Watch pending、快捷指令、Share Extension、iPad 批量入账和 Mac CSV 导入都必须有幂等键或重复检测。
6. 明确同步健康状态：用户需要知道当前数据是已同步、等待同步、离线、冲突待处理还是仅来自本机快照。
7. 明确隐私边界：默认不上传真实截图、OCR 全文、支付截图、小票图片或调试包；若未来同步 raw input，必须在 UI 中明确提示。

GOAL-1563 审计结论（2026-06-02）：

| 数据 / 通道 | 当前实现事实 | 可复用点 | v1.5.0 同步缺口 |
|-------------|--------------|----------|-----------------|
| 正式账单 `transactions` | App Group SQLite；含 `id`、`created_at`、`updated_at`、`deleted_at`，删除为软删除 | 已有稳定主键和软删除字段，可作为增量同步基础 | Swift `Transaction` 模型未暴露 sync metadata；缺少 `ledger_id`、`syncRevision`、`deviceId`、冲突状态和来源幂等键 |
| 订阅 `subscriptions` | SQLite + BackupBundle v1 | 可进入后续同步范围 | 当前缺少删除 / 归档语义和同步冲突字段 |
| 分类修正 / 商户别名 | SQLite 表含 `updated_at`，BackupBundle v1 会导出 | 可按 key 做 last-writer-wins 的早期同步 | 缺少删除 tombstone、device/source metadata 和冲突诊断 |
| 自定义分类 / 来源 | 主要在 UserDefaults，BackupBundle v1 导出数组 | 可先随 BackupBundle 恢复，后续迁入 SQLite | 不是结构化 per-item 数据，无法可靠做多端增删合并 |
| 多账本 | 目前只有文档约定的 `default-local-ledger` | 可作为旧数据迁移目标 | 尚无 `Ledger` model、`ledger_id` 和默认账本迁移代码 |
| 候选账单 / raw input | 尚未编码 | 可先默认排除同步，降低隐私风险 | 若未来同步，必须先实现隐私开关、加密/最小化字段和用户提示 |
| BackupBundle / iCloud Drive | `BackupBundle.schemaVersion = 1`；iCloud Drive 写入单个 `AutoLedgerBackup.json` | 适合手动迁移、灾备恢复、单设备重装恢复 | 单文件覆盖没有多端增量、冲突合并和删除合并能力，不能作为无感多端同步 |
| WatchConnectivity | iPhone 推送最近账单、今日摘要和自定义分类；Watch 可离线 pending 回传 | 可继续承担 Watch 轻写入和近实时摘要 | 不是完整账本复制，不能替代 iPhone / iPad / Mac 的账本同步 |
| Widget / App Group | Widget 只读本机 App Group SQLite | 本机今日支出和负一屏展示已经可用 | 不能看到其他设备最新数据；后续应读取本机同步后的快照，而不是直接联网 |
| iCloud entitlement | 当前为 `CloudDocuments` / ubiquity container | 支持现有 iCloud Drive 备份链路 | 若引入 CloudKit private database，需要额外 capability、entitlements、provisioning 和 Xcode Cloud 验证 |

v1.5.0 最小同步策略冻结：

1. 保持 local-first：本机 SQLite 继续作为运行时事实源；同步层只负责跨设备复制和合并，不引入服务端账户系统作为 v1.5.0 前置条件。
2. 优先采用 CloudKit private database 作为结构化多端同步方向；iCloud Drive BackupBundle 继续作为备份、导出、恢复和人工迁移工具，不承担静默多端合并。
3. GOAL-1564 必须先补同步元数据与冲突模型，再进入任何 CloudKit 编码；不得把现有 `AutoLedgerBackup.json` 扩展成会互相覆盖的“自动同步”。
4. v1.5.0 最小同步范围先覆盖正式账单、软删除、多账本元数据、自定义分类 / 来源、分类修正和商户别名；候选账单、OCR 全文、原始图片、支付截图、小票图片和调试包默认不进入同步。
5. iPhone、iPad、后续 Mac Catalyst 是主可写端；Apple Watch 保持轻写入端，通过 pending 队列回传给主账本；Widget、tvOS、visionOS 首版只读展示本机同步后的稳定快照。
6. 删除、批量清洗、CSV / JSON 导入、快捷指令、Share Extension 和 Watch pending 都必须带幂等键或可诊断重复检测，避免多端重复入账。
7. 若 CloudKit capability / provisioning / Xcode Cloud signing 未就绪，则把结构化同步标记为 `MANUAL_MIGRATION_REQUIRED`，不得为了上线全平台展示而降低发布链安全。

推荐实现顺序：

1. GOAL-1563：多端同步现状审计与策略冻结，先决定 iCloud Drive BackupBundle 增量、CloudKit private database 或混合方案。
2. GOAL-1564：基础同步元数据和冲突模型，补齐 `updatedAt`、`syncRevision`、`deviceId`、`deletedAt`、幂等键等最小字段设计。
3. GOAL-1565：iPhone / iPad / Mac Catalyst 账本同步最小闭环，先覆盖正式账单、多账本和自定义分类 / 来源。
4. GOAL-1566：Watch / Widget / 展示端快照同步，保证只读端和轻写入端读取同一稳定快照。

在 GOAL-1563～1566 完成前，Mac、tvOS、visionOS 不应进入“可发布质量”判断；iPad 可以继续做本机工作台，但必须在文档和 UI 中避免暗示多设备实时一致。

#### 5.9.3 schema version 策略

当前迁移依赖列存在性判断，短期可以继续兼容；进入多账本与候选队列前，建议补一个明确版本机制：

| 方案 | 建议 |
|------|------|
| `PRAGMA user_version` | 推荐用于本地 SQLite schema 主版本，轻量、无需新表 |
| `schema_migrations` 表 | 后续如果 migration 很多，可记录每次 migration id、执行时间和结果 |
| 列存在性迁移 | 保留用于兼容历史小迁移，但不再作为复杂 schema 的唯一依据 |

建议迁移顺序：

1. 读取 `PRAGMA user_version`；旧库视为 `0`。
2. 在 transaction 内逐步执行 v1、v2、v3 迁移。
3. 每步成功后更新 `user_version`。
4. 任何一步失败都 rollback，保持旧库可继续打开。

#### 5.9.7 BackupBundle v2 草案

BackupBundle v2 应保持“正式账本恢复优先、候选原始输入谨慎导出”的策略。

v2 建议新增：

| 字段 | 说明 |
|------|------|
| `ledgers` | 多账本列表，至少包含默认账本 |
| `transactionExtensions` 或扩展后的 `BackupTransaction` | `ledgerId`、`transactionType`、`currencyCode`、`originalAmount`、`exchangeRate` |
| `candidateBatches` | 可选导出导入批次摘要 |
| `candidateTransactions` | 可选导出候选账单字段，不默认包含原图 |
| `rawInputs` | 默认不导出；只有用户选择完整备份 / 诊断备份时才包含安全摘要或原始文本 |
| `customCategoriesV2` / `customSourcesV2` | 带 ID、排序、归档状态的结构化版本 |
| `cleaningActions` | 可选导出清洗历史，便于审计和回滚 |

兼容要求：

- `BackupValidator` 需接受 v1 和 v2，不能只判断 `schemaVersion == 1`。
- 解码 v1 文件时不能因为 v2 新字段缺失而失败；需要 optional 字段、默认值或自定义 `Decodable`。
- 恢复 v1 文件时，所有正式账单进入 `default-local-ledger`，`currencyCode = CNY`，`transactionType = expense`。
- v2 自动 iCloud 备份默认不包含原始图片、PDF 或 OCR 全文；若提供完整备份，UI 必须明确提示可能包含敏感财务数据。
- CSV 导出只覆盖正式账单，不包含候选区、raw input、debug events 或清洗历史。

#### 5.9.8 推荐实施顺序

| 顺序 | 目标 | 说明 |
|------|------|------|
| 1 | 引入 schema version | 使用 `PRAGMA user_version`，保留旧列检测兼容 |
| 2 | 新增 `ledgers` 表 | 插入 `default-local-ledger` |
| 3 | 扩展 `transactions` 表 | 添加 `ledger_id`、`transaction_type`、`currency_code` 等 additive columns |
| 4 | 回填旧账单 | 所有旧账单归入默认账本，不改变业务字段 |
| 5 | 新增候选区表 | `import_batches`、`raw_inputs`、`candidate_transactions`、`candidate_events` |
| 6 | 加查询 API | 先提供只读 / 写入候选区 API，再接 UI |
| 7 | BackupBundle v2 | 先支持读取 v1 + 导出 v2，再启用恢复 v2 |
| 8 | 迁移自定义分类 / 来源 | 从 UserDefaults 迁入 SQLite，同时保留 UserDefaults 同步兼容期 |

#### 5.9.9 回归要求

后续编码 GOAL-1503 方案时，至少补齐：

- 旧 SQLite 空库初始化成功。
- 旧 SQLite 有账单时迁移成功，旧账单进入 `default-local-ledger`。
- 重复运行迁移不会重复创建默认账本或破坏交易数据。
- `loadTransactions()` 默认不返回已删除账单、不返回候选账单。
- v1 BackupBundle 仍可恢复。
- v2 BackupBundle 缺少候选区字段时仍可恢复正式账单。
- 候选区表写入后不影响今日支出、月报和 Watch / Widget 数据。
- iCloud 自动备份不意外包含 raw input 敏感内容。

## 6. Mac Catalyst 主线

iPad 端程序完善后，Mac 端优先采用 Mac Catalyst 路线承接 iPad 工作台能力。Mac 不再只是“能不能复用”的评估项，而是 v1.5.x / v1.6.0 的明确全平台扩展方向。

Mac 端定位为桌面账本整理与导入导出工作台，重点不是快速记一笔，而是处理大量文件、批量修正、表格编辑和备份导入导出。

### 6.1 可直接复用的部分

- 账单数据模型、账本模型、候选账单状态模型。
- OCR 后文本解析、商户别名、分类学习、重复检测等 core 逻辑。
- SQLite / 本地持久化层中与平台 UI 无关的部分。
- iCloud Drive 备份、导入导出、离线回归样本和 Golden Case。
- SwiftUI 中足够纯粹的列表、表格、筛选器、详情检查器组件。
- iPad 截图管线中用于准备演示数据、固定状态和多语言文案的脚本思路。

### 6.2 Mac 首版能力

Mac Catalyst 首版建议覆盖以下能力：

| 能力 | 说明 | 依赖 |
|------|------|------|
| 拖拽截图 / 文件导入 | 支持从 Finder 拖入图片、PDF、文本文件或文件夹；进入导入队列而不是直接入账 | iPad 批量导入队列、macOS 文件权限 |
| CSV / JSON 导入导出 | CSV 用于表格交换，JSON 用于完整备份 / 迁移；导入必须有预览和确认 | BackupBundle、导入队列、字段映射 |
| 键盘快捷键 | 导入、导出、搜索、新增、编辑、删除、批量选择、确认入账、撤销等 | SwiftUI commands / Catalyst 菜单 |
| 大表格 / 列表编辑区域 | 更高密度表格、可排序列、可筛选列、详情检查器常驻 | iPad 账本工作区与候选区组件 |
| 批量选择 / 批量修正 | 多选账单后批量改分类、商户别名、来源、目标账本 | 数据清洗预览与事务写入 |
| 重复账单检查 | 按金额、商户、时间、OCR 文本相似度和来源提示重复 | 重复检测服务 |
| 基础菜单栏 | `Import` / `Export` / `Backup` / `Settings` 菜单，后续可扩展 Help / Window | Catalyst commands |

### 6.4 需要单独适配的部分

- Mac 窗口、菜单栏、快捷键、工具栏和多窗口行为。
- 文件导入体验：Mac 更依赖 Finder 拖拽、菜单导入、文件夹批处理。
- 表格密度和键盘操作：Mac 用户会期待更强的批量选择、复制、撤销和快捷键。
- 沙盒权限、文件访问、安全范围书签等 macOS 细节。
- App Store 截图、审核说明和平台能力描述需要单独准备。
- Watch / Widget 联动在 Mac 端不是核心卖点，不能简单复制 iPad 叙事。

### 6.5 产品判断

v1.5.0 首版建议按“iPad 优先，Mac Catalyst 跟进”处理：

- iPad 工作台先跑通批量导入、批量识别、清洗和多账本。
- 所有核心业务逻辑尽量放在跨平台模块，避免绑死 iPad UI。
- SwiftUI 组件拆分时考虑 macOS 可用性，但不为 Mac 牺牲 iPad 首版体验。
- 当 iPad 端候选账单、清洗队列、多账本管理稳定后，优先开启 Mac Catalyst 工程接入。
- Mac 端第一版不承诺 Watch / Widget parity，也不做复杂多窗口；先保证文件导入、表格整理和导入导出闭环。

结论：工程上可以复用大部分业务层和部分 SwiftUI 组件；产品上不把 Mac 端放进 App Store v1.4.0 的首版承诺，但把 Mac Catalyst 明确列为 iPad 端稳定后的下一阶段生产力平台。

### 6.6 tvOS 只读大屏看板

tvOS 不承担导入、编辑、清洗和写入账本，首版只做美观、稳定、可远距离阅读的只读展示。它更接近家庭大屏财务看板，适合在客厅查看家庭消费状态。

#### 6.6.1 tvOS 展示内容

- 本月支出总览：总金额、笔数、日均支出、与上月对比。
- 分类占比：餐饮、购物、交通、数字服务等分类的占比和金额。
- 最近消费趋势：最近 7 / 30 天消费折线或柱状趋势。
- 年度 / 月度摘要：年度累计、月度对比、Top 分类和 Top 商户。
- 家庭大屏看板：以大字号、低信息密度和清晰颜色层级展示，适配遥控器焦点导航。

#### 6.6.2 tvOS 设计边界

- 只读，不新增账单、不导入文件、不批量修正。
- 依赖 iCloud / 本地共享数据或后续同步方案；不为 tvOS 单独设计账本写入链路。
- 遥控器操作只做时间范围、账本、分类焦点切换。
- 必须有隐私模式，避免家庭大屏直接暴露具体账单明细。

### 6.7 visionOS 空间展示版本

visionOS 首版定位为漂亮的空间展示体验，不替代 iPad / Mac 的生产力工作台。它强调“看见自己的消费结构”，而不是在空间里做复杂表格编辑。

#### 6.7.1 visionOS 展示内容

- 月度支出空间看板：总览指标以大卡片形式固定在主视线区域。
- 分类支出卡片漂浮展示：分类金额、占比、变化趋势以卡片组展示，可按分类聚合。
- 年度消费时间线墙：按月份排列年度支出、Top 分类、异常月份和重要事件。
- 最近账单悬浮列表：展示最近消费摘要，支持轻量筛选和只读详情。

#### 6.7.2 visionOS 设计边界

- 首版只读展示，不做拖拽文件导入、批量编辑或数据清洗。
- 视觉重点是空间层次、阅读距离、手势焦点和低疲劳信息密度。
- 数据口径必须与 iPad / Mac / iPhone 一致，避免展示端产生另一套统计逻辑。
- 隐私模式必须可用，金额和商户可一键隐藏。

## 8. 识别链路优化

### 8.1 目标

v1.5.0 继续强化“识别 → 解释 → 复核 → 入账”的可信链路。

重点不是让系统永远自动判断正确，而是在不确定时明确告诉用户：

- 哪些字段可信。
- 哪些字段需要复核。
- 为什么被归到某个商户或分类。
- 是否可能重复。
- 是否适合批量应用同样规则。

### 8.2 场景拓展

优先补充以下场景样本和规则：

- 微信支付、支付宝、Apple Pay、银行卡消费通知。
- 电商订单和支付详情。
- 订阅服务账单。
- 餐饮、小票、外卖、咖啡、便利店。
- 出行、打车、地铁、停车、酒店、机票。
- 海外消费、多币种金额、汇率备注。
- 邮件 / 短信 / 剪贴板文本账单。
- 长截图、多张截图组成的一笔账单。

### 8.3 质量门禁

每次拓展识别场景时，应同步增加：

- Golden Case。
- 离线回归样本。
- 误识别反例。
- 低置信度展示规则。
- 分类 / 商户别名回归检查。

### 8.4 平台无关解释器收口方向（GOAL-1594）

当前工程已经存在平台无关层 `AutoLedgerCore/Sources/AutoLedgerCore/Services/LedgerTextInterpreterCore.swift`，并且它已经能输出 `InterpretResult` / `TransactionDraft`。但 v1.5.0 当前主链路还没有把它作为最终“文本 -> 结构化账单”责任层使用到底。

#### 8.4.1 当前事实

| 层级 | 当前职责 | 当前问题 |
|------|----------|----------|
| `LedgerTextInterpreterCore`（Core） | 非账单拦截、基础金额 / 商户 / 分类草稿、批量小票 core 回归 | App 主入账链路目前主要使用其 `nonBillImage` 判断，最终账单字段仍不主要来自 Core |
| `LedgerTextInterpreter`（App adapter） | 统一 OCR / 语音 / 订阅 / 智能解析入口 | 同时持有 Core、`SmartReceiptParser`、`ReceiptParser`，职责仍偏协调和兼容 |
| `SmartReceiptParser`（App） | LLM-first，低置信度或不可用时规则兜底 | 规则兜底仍调用 App 层 `ReceiptParser` |
| `ReceiptParser`（App） | 微信、支付宝、淘宝闪购、云闪付、滴滴、抖音、美团等真实平台规则 | 平台规则继续堆在 App target，不利于 Watch / Mac / Worker / 批量导入复用 |
| `QuickLedgerIntent` / Share Extension | 快捷指令和扩展入口 | 仍可绕过 Core 最终解析，直接走 `SmartReceiptParser` / `ReceiptParser` 兼容路径 |

结论：平台无关层已经抽出，但当前还没有成为唯一或主要的结构化账单生成层。v1.5.0 后续应把文本解析能力从“App 层平台规则优先”收口为“Core 候选实体 + 评分 + 可选本地 AI rerank + App adapter 保存”。

#### 8.4.2 目标链路

目标链路如下：

```text
OCR / 语音 / 剪贴板 / 邮件文本
  → App adapter 只做来源 hint、OCR 清洗、LLM provider 选择
  → AutoLedgerCore 文本标准化与分段
  → Core 抽取候选实体
       - amountCandidates
       - dateCandidates
       - merchantCandidates
       - productDescriptionCandidates
       - platformNameCandidates
       - paymentMethodCandidates
  → Core 确定性评分与解释
  → 可选本地 AI rerank（只在候选冲突 / 低置信时介入）
  → TransactionDraft / CandidateTransaction
  → App adapter 复核、入账、商户别名、分类学习、SQLite / CloudKit
```

#### 8.4.3 候选商户原则

商户识别不应只依赖“某一行位置”，而应先形成候选池再评分：

| 候选类型 | 示例 | 分数倾向 |
|----------|------|----------|
| 字段值候选 | `商品说明`、`商户名称`、`收款方` 后的值 | 高 |
| 展示商户候选 | 金额附近、标题附近的品牌 / 店铺行 | 中高 |
| 订单说明候选 | `LINLEE林里•手打柠檬茶（南开海光MALL店）外卖订单` | 高，但需清理订单后缀 |
| 平台名候选 | `淘宝闪购`、`支付宝`、`微信支付`、`云闪付` | 默认降权，除非没有更具体商户 |
| 支付工具候选 | 银行卡、付款方式、支付机构 | 排除或极低分 |
| UI 噪声候选 | `更多`、`账单管理`、`请选择`、按钮文案 | 排除 |

#### 8.4.4 AI 介入边界

AI 不应自由从全文生成商户名作为默认路径。推荐只在 Core 已提取候选后做本地 rerank：

- 输入：脱敏或原始本地文本片段、候选列表、候选来源、候选分数。
- 输出：选择的候选 ID、置信度、简短 reason。
- 约束：不能输出候选列表之外的新商户，除非进入 `needsReview`。
- 隐私：继续端侧执行，不上传 OCR 原文、支付截图或调试包。

#### 8.4.5 分阶段 GOAL

后续不再把平台真实样本修复默认继续堆到 App 层 `ReceiptParser`。每次遇到新样本，先判断是否能沉淀为 Core 候选实体 / 字段块 / 评分规则；只有需要 iOS 专属能力时才保留在 App adapter。

## 10. 验收口径

### 10.1 Watch

- 打开 Watch App 首屏即能看到今日支出总金额、笔数和最近商户。
- 向左滑第二屏能看到当前账本关联的最近支出。

- 大字号、VoiceOver、隐私隐藏场景可用。

### 10.2 iPad

- iPad 上可以完成一批截图或文件的导入。
- 批量识别结果进入候选区，而不是直接污染正式账本。
- 用户可以批量确认、逐条修正、忽略或重试。
- 用户可以对商户、分类、重复项进行清洗整理。
- 候选账单确认后能结构化写入指定账本。
- 统计分析能按账本、月份、分类、商户查看。
- iPad 截图管线能导出稳定的工作台、批量导入、清洗和多账本页面。
- iPad 截图产物能进入统一 `preview.html`，并能按 locale 分别目检。

### 10.3 Mac Catalyst

- iPad 工作台稳定后，Mac Catalyst 工程能复用核心模型、解析、导入队列、清洗和备份能力。
- Mac 进入可发布质量前，必须与 iPhone / iPad 使用同一基础同步策略，不能只读写本机独立账本。
- Mac 支持拖拽截图 / 文件导入，导入内容进入候选区或导入预览，不直接污染正式账本。
- Mac 支持 CSV / JSON 导入导出；恢复类操作必须有预览和确认。
- Mac 支持键盘快捷键和基础菜单栏：Import / Export / Backup / Settings。
- Mac 提供更大的表格 / 列表编辑区域，支持排序、筛选、搜索和详情检查器。
- Mac 支持批量选择、批量修正和重复账单检查，批量写入前必须展示影响范围。

### 10.4 tvOS

- tvOS 首版只读，不提供导入、编辑、删除、清洗或备份恢复。
- tvOS 必须读取来自主账本的稳定同步快照，不维护独立账本。
- 本月支出总览、分类占比、最近消费趋势、年度 / 月度摘要能在远距离清晰阅读。
- 家庭大屏看板支持遥控器焦点导航和隐私隐藏。
- tvOS 展示口径与 iPhone / iPad / Mac 的统计口径一致。

### 10.5 visionOS

- visionOS 首版只读展示，不提供复杂表格编辑或文件导入。
- visionOS 必须读取来自主账本的稳定同步快照，不维护独立账本。
- 月度支出空间看板、分类支出卡片、年度时间线墙和最近账单悬浮列表布局清晰。
- 空间展示支持隐私隐藏，避免金额和商户在共享空间中直接暴露。
- visionOS 展示口径与其他平台一致，不新增独立统计逻辑。

### 10.6 识别链路

- 新增场景必须有样本和回归。
- 低置信度结果必须清楚标记。
- 批量规则应用前必须让用户确认影响范围。
- 商户别名、分类学习、重复检测不能破坏既有账单数据。

### 10.7 基础多端数据同步

- iPhone 与 iPad 至少能在同一 Apple ID 下完成基础账本同步或明确的受控恢复，不依赖手动反复导入 JSON。
- 多端新增、编辑、删除同一账单时有可解释的最终状态，不静默丢失用户数据。
- Watch pending 写入回传后不会重复入账，且今日支出 / 最近支出能在合理时机刷新。
- Widget、tvOS、visionOS 读取的统计快照与主账本口径一致，并能显示过期 / 离线状态。
- 同步范围不默认包含真实截图、OCR 全文、小票图片、支付截图或调试包。
- 同步失败、冲突待处理、仅本机数据等状态需要对用户可见或至少可诊断。

## 11. 风险与待确认问题

- Watch 小组件刷新频率受系统限制，不能承诺实时金额。
- 今日支出口径需要与多账本能力提前对齐，避免后续迁移成本过高。
- Watch 左滑第二屏与快速记账入口的导航层级需要实机验证，避免常用操作变深。
- iPad 批量导入可能引入大量候选数据，需要设计失败恢复和取消路径。
- PDF、长截图、多币种等场景复杂度较高，需要明确首版支持边界。
- 多账本涉及现有账单数据迁移，必须先设计默认账本和兼容策略。
- 基础多端同步若不先解决，iPad / Mac / tvOS / visionOS 会变成各自孤立数据岛；v1.5.0 不应在该问题未收口时宣称全平台数据一致。
- iCloud Drive 单文件备份不是实时同步；若继续沿用 BackupBundle，需要明确手动 / 自动恢复边界和冲突策略。
- 若引入 CloudKit private database，需要额外验证 Apple Developer capability、entitlements、Xcode Cloud signing、离线冲突、删除合并和隐私披露。
- 数据清洗动作可能影响历史账单，必须有确认、预览和回滚思路。
- iPad 到 Mac 可以复用大量业务层，但 macOS 交互、菜单、文件权限、拖拽导入、安全范围书签和窗口体验需要单独设计。
- Mac Catalyst 可能暴露 iPad UI 在桌面上的密度和焦点问题，必须单独做键盘、菜单、表格和批量操作验收。
- tvOS 与 visionOS 不应抢跑写入能力；展示端如果没有稳定同步 / 共享数据口径，容易出现与主账本不一致。
- tvOS 家庭大屏和 visionOS 空间展示都需要隐私隐藏策略，避免在公共空间暴露个人消费明细。
- App Store v1.4.0 是否同时发布 iPad 截图、Watch 小组件截图，需要根据实现质量再定。
- 当前截图管线不支持 iPad；v1.5.0 若要发布 iPad 端，必须预留足够时间实现、导出并人工复核 iPad 截图。

## 13. 计划评审与 GOAL 拆解

### 13.1 评审结论

当前 v1.5.0 规划方向成立，并已扩展为全平台路线：iPhone / Watch 负责快速记录与随手查看，iPad 负责整理工作台，Mac Catalyst 承接桌面生产力，tvOS 和 visionOS 承接只读展示。若直接从 UI 开始实现，容易出现以下问题：

- 多账本、候选账单、批量识别状态没有底层模型时，iPad 工作台只能做静态页面，后续返工成本高。
- Watch 今日支出和表盘小组件依赖“今日支出统计口径”，该口径又会受到多账本影响，需要先做一个兼容默认账本的最小口径。
- iPad 批量导入、数据清洗和截图管线都需要同一套稳定演示数据，应在 UI 与截图脚本前统一 fixture。
- 基础多端同步必须在 Mac Catalyst 和只读展示平台前收口，否则 iPhone / iPad / Mac / Watch / Widget / tvOS / visionOS 会出现数据岛。
- Mac Catalyst 不应在 iPad 和同步底座稳定前抢跑，但 iPad 的模型、队列、清洗、表格和导入导出能力必须提前按桌面可复用方式拆分。
- tvOS / visionOS 不应引入写入账本能力，展示端必须跟随统一统计口径、同步快照和隐私策略。
- iPad 截图管线必须排在 iPad 工作台可展示之后，但不能拖到发布最后一天才补。

因此 v1.5.0 应按“底座 → Watch 小闭环 → iPad 工作台 → 批量与清洗 → 多账本 → 基础多端同步 → Mac Catalyst → 只读展示平台 → 发布资产”的顺序推进。每个 GOAL 都应能单独提交、单独回归、单独回滚。

### 13.2 GOAL 执行规则

每个 GOAL 进入实现前，先按 `process/agent-iteration-workflow.md` 写执行前检查，明确：

- 本轮只完成该 GOAL，不顺手做后续 GOAL。
- 若触碰 Xcode project，必须保持 scheme、target、bundle id、entitlements、Xcode Cloud 脚本不被重命名或删除。

### 13.43 iCloud 启动同步顺序修正（2026-06-03）

状态：DONE（启动自动同步改为先推送本地增量，再拉取远端）。

用户真机同步测试中观察到：早上记录的一笔账单在同步测试过程中消失，之后手动补齐。用户确认同步过程中没有主动删除记录。结合当前链路检查，旧启动策略存在一个顺序风险：App 启动自动同步只做远端拉取，外部入口或上次退出前未及时推送的本地增量可能还未先进入 CloudKit。

#### 13.43.1 风险判断

| 风险点 | 判断 |
|--------|------|
| 用户主动删除 | 用户确认没有发生 |
| 本地新增后 2 秒延迟推送尚未执行，App 被关闭或切走 | 可能，旧逻辑依赖后续启动 / 回前台补推 |
| 旧启动自动同步先拉取远端 | 确认存在，旧 `syncLedgerWithCloudKitOnLaunchIfNeeded()` 只调用 pull |
| 远端 tombstone 覆盖本地同 ID | 理论存在，但 UUID 碰撞概率极低；更可能是“本地未推、其他设备未见、用户以为消失”或刷新口径误判 |
| 全量 pull 无 server change token | 已知问题，会放大首次同步和排查成本，但不是本轮直接修复目标 |

#### 13.43.2 本轮修复

| 文件 | 内容 |
|------|------|
| `AutoLedger/AutoLedger/App/LedgerStore.swift` | 启动自动同步改为先调用 `pushLedgerChangesToCloudKitIfEnabled`；推送成功后清理外部入口 pending 标记，再执行远端拉取；推送失败时暂停本次拉取 |
| `AutoLedger/AutoLedger/App/AutoLedgerApp.swift` | 移除启动同步后的额外 pending 补推调用，避免启动链路重复推送 |
| `CHANGELOG.md`、`process/iteration-log.md`、`versions/v1.5.0-plan.md` | 记录启动同步顺序修正、风险判断和真机复测口径 |

#### 13.43.3 新启动同步口径

App 启动且 iCloud 同步开启时：

1. 首屏先渲染，约 1.5 秒后启动后台同步任务。
2. 先增量推送本机正式账单、软删除 tombstone 和配置快照。
3. 本机推送成功后，清理快捷指令 / Share Extension 等外部入口的待推送标记。
4. 再拉取远端账单和配置。
5. 如果本机推送失败，本次启动同步暂停远端拉取，避免在本地变更未上云时先合并远端状态。

账本页下拉刷新仍保持只拉取远端，用于用户主动获取其他设备最新数据；手动“强制刷新数据”仍保持全量推送 + 拉取。

#### 13.43.4 真机复测建议

1. iPhone 新增一笔明显测试账单后立即杀掉 App。
2. 重新启动 iPhone App，等待启动后台同步完成，查看同步日志应先出现“App 启动，先推送本地增量到 iCloud”。
3. 打开 iPad App，等待启动后台同步或下拉账本页，确认该笔账单出现。
4. iPad 新增一笔测试账单后重复同样步骤，在 iPhone 验证拉取。
5. 用快捷指令新增一笔后打开主 App，确认启动同步会先推本机增量并清理 pending 标记。
