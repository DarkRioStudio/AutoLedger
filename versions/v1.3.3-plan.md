# v1.3.3 版本计划

更新日期：2026-04-27
文档状态：Implemented（首轮核心 + gate + 批量工具骨架）
关联设计：`docs/architecture/LedgerTextInterpreter.md`、`versions/v1.3.2-plan.md`

## 1. 版本定位

- 版本号：v1.3.3
- 承接版本：v1.3.2
- 版本主题：平台无关 `LedgerTextInterpreter` 核心 + 小票图片集批量 OCR/批量测试
- 核心目标：
  - 将 v1.3.2 App 层的解释器编排能力，抽象为可测试、可复用、尽量平台无关的核心解析模块。
  - 在 OCR 后新增账单相关性判断，识别与账单无关的图片，并向用户提示图片没有有效账单信息。
  - 建立从 `receiptsample/` 小票图片集到批量 OCR、批量解析、Golden Case 回归报告的工具链。
  - 让真实小票样本成为后续解析规则、AI prompt 和商户识别优化的持续回归基线。

## 2. 当前工程基础

v1.3.2 已完成：

- `LedgerTextInterpreter` 统一承接 OCR 文本、语音文本、Siri 文本和一句话输入。
- App 内普通账单通过 `LedgerStore.createTransaction(from:)` 进入原有入库链路。
- 语音/一句话/Siri 已进入解释器的 `.voice` 分支。
- `docs/architecture/LedgerTextInterpreter.md` 已明确目标：`Text -> TransactionDraft`，并要求平台无关、入口无关、可测试。

当前限制：

- `LedgerTextInterpreter.swift` 仍位于主 App target，依赖 `SmartReceiptParser`、`LLMProvider` 和 App 层服务。
- `SmartReceiptParser` 依赖 `FoundationModels`、Gemma 服务与 App target，不适合作为纯核心层。
- `AutoLedgerCore` 当前仍含 `OCRService`、`ReceiptParser` 中的 Vision 相关代码，严格意义上不是完全平台无关。
- `receiptsample/` 已被 `.gitignore` 排除，适合作为本地大样本测试数据源，但不能作为仓库内测试 fixture 直接提交。

## 3. 目标架构

```text
receiptsample/ 本地图片集
        |
        v
Batch OCR Tool
  - 读取 jpg/png/heic/pdf? 图片
  - 使用 Apple Vision OCR
  - 输出 raw text + confidence + image metadata
        |
        v
Bill Relevance Gate
  - 判断 OCR 文本是否包含有效账单信息
  - 无关图片输出 non_bill_image，不进入解析
        |
        v
Batch Parse Runner
  - 调用平台无关 LedgerTextInterpreterCore
  - 输出 TransactionDraft / warning / debugTrace
        |
        v
Golden Case Store
  - 可提交的脱敏文本 case
  - 不提交原始图片
  - 支持失败差异报告
        |
        v
CI / Local Regression
  - 规则回归
  - OCR 样本质量统计
  - 解析准确率趋势
```

App 内运行时架构：

```text
OCR / Voice / Siri / Clipboard / Manual
        |
        v
Text Adapter
  -> InterpretInput
        |
        v
LedgerTextInterpreterCore
  -> InterpretResult(TransactionDraft?)
        |
        v
App Adapter
  -> ImportedReceipt / VoiceLedgerParseResult / Subscription
        |
        v
LedgerStore.createTransaction / upsertSubscription
```

## 4. 核心设计

### 4.1 新增平台无关数据结构

计划新增 Swift 纯模型，优先放在新的核心 target；若 target 拆分风险过高，则先放入 `AutoLedgerCore` 的平台无关目录并移出 Vision 依赖路径。

```swift
public struct InterpretInput: Sendable, Codable {
    public var rawText: String
    public var sourceType: LedgerInputSourceType
    public var localeIdentifier: String?
    public var timeZoneIdentifier: String?
    public var hints: LedgerInterpretHints
    public var categoryCorrections: [String: String]
}

public enum LedgerInputSourceType: String, Sendable, Codable {
    case ocr
    case voice
    case siri
    case clipboard
    case manual
    case share
    case subscriptionEmail
}

public struct TransactionDraft: Sendable, Codable, Equatable {
    public var amount: Double
    public var merchant: String
    public var category: String
    public var occurredAt: Date
    public var sourceType: LedgerInputSourceType
    public var inputText: String
    public var parseMethod: ParseMethod
}

public struct InterpretResult: Sendable, Codable, Equatable {
    public var draft: TransactionDraft?
    public var confidence: InterpretConfidence
    public var needsReview: Bool
    public var warnings: [InterpretWarning]
    public var debugTrace: [String]
}
```

新增 warning / failure 类型必须覆盖：

- `nonBillImage`：OCR 有文本，但缺少金额、商户、支付/小票/订单关键词等账单信号。
- `emptyOCRText`：OCR 未识别到文本。
- `missingAmount`：像账单，但没有可用金额。
- `multipleAmountsNeedsReview`：存在多金额，需确认或匹配总金额。
- `missingReliableTotal`：多商品小票没有可靠合计金额。

### 4.2 核心解释器职责

`LedgerTextInterpreterCore` 负责：

- 文本标准化。
- 来源/场景识别：receipt、payment、sentence、subscription。
- 账单相关性判断：在解析字段前先判断文本是否包含有效账单信号。
- 金额、商户、日期、分类草稿提取。
- 多金额、多商品小票、无总金额等 warning 输出。
- 置信度归一化：high / medium / low。
- 输出 `TransactionDraft` 和可测试的 `debugTrace`。

`LedgerTextInterpreterCore` 不负责：

- Vision OCR。
- LLM 模型调用。
- SQLite。
- Widget。
- iCloud。
- UI 文案。
- 商户别名持久化。

### 4.3 App Adapter 职责

App 层保留：

- `SmartReceiptParser` 的 LLM 增强。
- `LLMProvider`、Gemma、FoundationModels。
- `LedgerStore` 入库、副作用和用户学习。
- 将 `InterpretResult` 转换为当前 App 所需的 `ImportedReceipt` 或确认页草稿。

### 4.4 与 v1.3.2 的兼容策略

- 保留现有 `LedgerTextInterpreter` 作为 App adapter，逐步改为调用 `LedgerTextInterpreterCore`。
- 第一阶段不要求一次性删除 `LedgerTextInterpretation`。
- `TransactionDraft` 先作为核心输出，App adapter 再映射到 `ImportedReceipt`。
- 对语音短句，先让 `VoiceLedgerParser` 迁入或包裹到核心层；UI 仍调用 `LedgerStore.interpretVoiceText`。

## 6. Golden Case 设计

计划新增可提交的脱敏文本样本：

```text
tests/golden/ledger_text_interpreter/
  cases.jsonl
  README.md
```

Case 示例：

```json
{
  "id": "scanned_receipt_0001",
  "source_type": "ocr",
  "raw_text": "STORE\nTOTAL 12.40\n...",
  "expected": {
    "amount": 12.4,
    "merchant": "STORE",
    "category": "groceries",
    "confidence": "high",
    "needs_review": false
  },
  "warnings": [],
  "privacy": "public_sample_redacted"
}
```

规则：

- Golden Case 只提交文本，不提交图片。
- 文本来自公共样本或已脱敏样本。
- 每个 case 必须有 expected amount。
- merchant 可分为 strict / loose 两种断言：
  - strict：必须完全匹配。
  - loose：允许非空或包含关键词。
- 对多商品小票，可断言必须识别总金额或必须输出 `missing_total` warning。
- 对非账单图片，可断言必须输出 `non_bill_image`，且不得生成 `TransactionDraft`。

## 7. OCR 后账单相关性判断

### 7.1 目标

用户可能导入风景照、聊天截图、普通网页、商品图、空白图片或无关文档。v1.3.3 需要在 OCR 完成后、字段解析前增加相关性判断：

```text
OCR image -> raw text -> Bill Relevance Gate -> LedgerTextInterpreterCore
```

无关图片不进入账单解析，不生成草稿，不写入账本。

### 7.2 判定信号

正向账单信号：

- 金额信号：`¥`、`￥`、`元`、`TOTAL`、`AMOUNT`、`支付金额`、`实付`、`合计`、`小计`。
- 交易信号：`付款成功`、`交易成功`、`支付成功`、`订单详情`、`交易详情`、`收款方`、`商户名称`。
- 小票信号：`receipt`、`invoice`、`tax`、`cashier`、`subtotal`、`grand total`。
- 平台信号：微信、支付宝、云闪付、银联、App Store、淘宝、饿了么、抖音等。

负向/不足信号：

- OCR 文本为空或极短。
- 只有日期、标题、聊天内容、网页导航、广告文案。
- 有金额样数字但没有交易、商品或商户上下文。
- 图片主要是自然图像，OCR 只识别到零散字符。

### 7.3 用户提示

App 内提示文案：

```text
图片没有有效的账单信息，请换一张支付截图或小票照片。
```

英文兜底：

```text
No valid bill information was found in this image.
```

调试记录：

- `stage`: parseFailed 或后续新增 `nonBillSkipped`。
- `warning`: `nonBillImage`。
- `rawText`: 保留 OCR 文本，供 Debug 页查看。
- `summary`: 用户可读提示。

### 7.4 批量测试要求

- 批量 OCR/解析报告需单独统计 `non_bill_image`。
- Golden Case 至少包含 5 条非账单文本：
  - 空白/无文本。
  - 普通聊天截图。
  - 普通网页截图。
  - 商品展示但无付款信息。
  - 风景/照片 OCR 零散字符。
- 非账单 case 必须断言不生成 `TransactionDraft`。

## 10. Out of Scope

- 不把 `receiptsample/` 原始图片提交到 Git。
- 不把 CORD parquet 全量数据转入仓库。
- 不在本版上线云端 Worker API。
- 不做 Android 端实现。
- 不要求 LLM 在批量测试中默认启用；批量测试默认走规则核心，LLM 只作为可选实验模式。

- 不改 App Store 用户可见主流程，除非接入 adapter 时必须修复编译或行为回归。

## 11. 风险与应对

- 风险：`AutoLedgerCore` 当前含 Vision 依赖，若直接放入同 target 仍不够平台无关。
  - 应对：优先新增更小的纯 Swift target，例如 `AutoLedgerInterpreterCore`；若 Xcode target 调整成本过高，先以目录隔离和 import 检查约束。
- 风险：真实小票 OCR 噪声很大，短期指标可能偏低。
  - 应对：先建立基线报告，不把准确率门槛设得过高；后续迭代逐步提升。
- 风险：账单相关性判断过严，可能误拦截弱格式小票或纯金额支付截图。
  - 应对：第一版只拦截低信号文本；低置信但疑似账单的图片进入 needsReview，不直接丢弃。
- 风险：公共样本文本可能仍包含敏感字段。
  - 应对：Golden Case 入库前做脱敏脚本和人工抽查；原始 OCR JSONL 默认输出到 `.tmp/`，不提交。
- 风险：核心类型引入后 App adapter 映射出现分类或来源差异。
  - 应对：保留 v1.3.2 回归样本，逐步替换，不一次性删除旧解释结果类型。

## 12. 回滚方案

- 保留 v1.3.2 的 App 层 `LedgerTextInterpreter` 行为作为回滚点。
- 若核心 target 或 adapter 接入造成 App 编译风险，可先关闭 App 接入，只保留 CLI 和 Golden Case 工具。
- 若账单相关性判断误拦截，可临时关闭 gate，只保留 `parseFailed` 提示。
- 批量 OCR/解析工具为开发工具，不进入用户主流程；失败时可从构建门禁中临时移除。

## 13. 后续演进

- v1.3.4：根据批量报告修复高频 OCR/解析失败样本。

- 后续：将商户别名、分类学习从入库副作用中抽象为可注入的解析 hint，而不是核心层直接持久化。
