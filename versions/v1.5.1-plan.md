## 1. 版本定位

`v1.5.1` 不再只是 `v1.5.0` 的补丁号，而是当前开发线正式承接版本。

本轮决策调整如下：

1. `v1.5.0` 已完成 iPhone / iPad / Apple Watch / Mac Catalyst 的主线能力铺设，以及截图、回归资料、Review Notes 等发布前基础准备。
2. `v1.5.0` 不单独做最终 smoke、Xcode Cloud 收口和提审动作；这些门禁延后到 `v1.5.1` 全部内容完成之后统一执行。
3. `v1.5.1` 承接两类任务：
   - `v1.5.0` 遗留的最终收口、smoke、Xcode Cloud 和 App Store Connect 动作
   - 全平台内容补齐与最低系统需求优化
   - `v1.5.0` 遗留的账单 OCR / 文本识别链路 Core 化重构
   - 脱敏外部大模型 API 辅助识别接入
4. 多账本继续顺延，不进入 `v1.5.1` 当前实现范围。

因此，`v1.5.1` 的真实角色是：

- `v1.5.0` 主线成果的整合版
- 全平台第一阶段闭环版
- 最低系统需求下调的实施版
- 识别链路平台无关核心能力的重构版
- 外部大模型辅助识别的受控试点版
- App Store `1.4.0` 的最终候选开发线

- 不允许为了通过低系统编译，把主流程、主页面、核心数据类型整体标记为 `@available(iOS 26.0, *)`
- 低系统主链路必须通过 `CoreBase / Adapter / Extension / FeatureGate` 分层实现
- `ClipboardImportIntent` 已迁出 `AutoLedgerCore`，后续 Core 继续保持 Foundation / SQLite / 通用服务边界
- `Intent Adapter`：`AppIntents`、控制组件等高层入口不进入 Core
- `FeatureGate`：Apple Foundation Models、Apple Intelligence 等增强能力继续保持 `iOS 26+` 可选路径

### 4.6 Shortcuts 结构化账单导入补充

为当前单账本主线补一条自动化入口：

- Shortcuts / 剪贴板可传入结构化账单 JSON
- App Intent 解析金额、商户、分类、日期、备注、币种和置信度
- 高置信度自动保存

- `currency` 暂存入备注，不新增币种字段

### 4.7 账单 OCR / 文本识别链路 Core 化重构

`v1.5.1` 承接 `v1.5.0` 遗留的识别链路稳定性目标，但本轮不再继续在 `ReceiptParser`、`SmartReceiptParser`、`LedgerTextInterpreterCore` 中分别堆叠互相牵扯的规则，而是将平台无关解析能力收回 `AutoLedgerCore`。

目标 Pipeline：

```text
OCR / 原始文本
-> TextClean + PaymentAmountExtractor
-> Merchant Extraction: 规则候选 + LLM 候选
-> MerchantResolver / MerchantNormalizer
-> CategoryResolver
-> TransactionDraft / ImportedReceipt 适配
```

核心原则：

- 金额只由规则提取，不由 LLM 决定。
- LLM 只辅助商户名称候选，不负责金额，不负责最终分类。
- 每条规则输出 `candidate + evidence + confidence`，不直接覆盖最终结果。
- 最终金额、商户和分类由 resolver 统一选择。
- 商户选择不再依赖 OCR 文本中的简单先后顺序，而是基于分词后的商户可能性、上下文证据、黑名单 / 白名单、支付渠道排除和历史别名信号综合排序。
- 平台无关逻辑必须留在 `AutoLedgerCore`，不得引入 `UIKit`、`SwiftUI`、`Vision`、`FoundationModels`、`CloudKit` 等平台依赖。
- 不改 UI、不改 SQLite schema、不改用户可见入账流程，优先做内部架构收口和回归稳定。

第一阶段目标：

- 在 `AutoLedgerCore/Sources/AutoLedgerCore/Services/` 新增平台无关解析模块。
- 将 `LedgerTextInterpreterCore` 里现有金额规则封装为 `PaymentAmountExtractor`，输出 `AmountExtractionResult`，包含 paid amount、候选、confidence、rule、evidence、debug 信息和近似标记。
- 将商户规则封装为 `RuleMerchantExtractor` / `MerchantExtractor`，输出 `[MerchantCandidate]`，候选包含 name、source、confidence、lineIndex、evidence、ruleName。
- 新增 `MerchantResolver`、`MerchantNormalizer`、`CategoryResolver`，让商户选择、商户标准化和分类推断从散落规则中独立出来。
- `MerchantResolver` 需要从“行序推断”升级为“候选评分”模型：先将 OCR 行拆成 merchant token / phrase candidate，再根据支付关键词距离、金额关键词距离、发票 / 小票标题噪声、支付渠道黑名单、主体名特征、历史别名和 LLM 候选一致性计算优先级。
- 修改 `LedgerTextInterpreterCore.interpret` 使用新的 Core Pipeline，保持公开 API 和 `TransactionDraft` 输出结构不变。
- 修改 App 层 `ReceiptParser.swift`，逐步复用 Core 层金额、商户 resolver 和分类 resolver；保留纸质小票、微信详情块、抖音 / 美团券码、滴滴、支付宝 / 淘宝、云闪付等现有特殊逻辑，避免一次性重写导致回归风险。
- 修改 `SmartReceiptParser.swift` 的职责边界：规则先锁定金额，LLM 只输出商户候选；分类仍走 `CategoryResolver`。如果本轮风险较高，可先保留旧入口并加适配层，但不得让 LLM 金额覆盖规则金额。
- 扩展 `scripts/OfflineRegression.swift`，新增 `PaymentAmountExtractor`、`MerchantResolver`、`MerchantNormalizer` 独立回归，并保留既有 `LedgerTextInterpreterCore` 样例。

外部 API 接入规划：

- 在默认本地识别链路之外，于 `v1.5.1` 接入第一版“脱敏数据解析增强”接口。
- 外部大模型 API 只能在用户主动开启的独立开关下使用，默认关闭。
- 外部增强仅接收脱敏 / 最小化后的结构化文本，例如移除订单号、卡号尾号、设备信息、地址、手机号、完整 OCR 原文和图片。
- 外部模型职责仍限定为商户候选、账单类型提示和低置信度解释，不得直接决定最终金额，也不得绕过用户确认。
- 该能力作为 `v1.5.1` 内部试点能力接入，可评估为后续低成本 Pro 功能；若 API 成本、隐私文案或稳定性未达标，可以在发布前保持隐藏 / Debug 开关，不阻塞主链路发布。
- 若未来接入，需要单独的隐私说明、开关 UI、失败降级、本地优先兜底、日志脱敏和回归样例，不得影响离线默认体验。

第一版接入边界：

- 新增 App 层外部解析 Adapter，不进入 `AutoLedgerCore`，Core 只接收脱敏后的候选结果。
- API key 不进入仓库，不写入源码，不进入截图、日志或回归样例。
- 请求只发送脱敏后的候选行、金额附近上下文摘要、支付渠道类型、OCR 来源类型和本地规则候选，不发送图片二进制和完整 OCR 原文。
- 返回值只允许转成 `MerchantCandidate` / `Category hint` / `reason` / `confidence`，不能直接生成正式 `ImportedReceipt`。
- UI 上使用独立开关，例如“增强识别（脱敏云端辅助）”，默认关闭，并明确可能使用外部模型服务。
- 低置信度或规则冲突时必须进入用户确认，不得静默入账。
- 网络失败、API 失败、配额耗尽或开关关闭时，本地规则链路必须完整可用。

重点覆盖场景：

- 微信支付独立负数金额行。
- 支付宝支付成功页中付款方式附近的真实商户。
- 小票 `TOTAL RM` / `GRAND TOTAL` / `AMOUNT DUE` / `BALANCE DUE` / `TOTAL SALES`。
- 优惠、红包、折扣、找零、现金支付、税额、数量、订单号、注册号、时间和商品编号排除。
- 多商品价格场景不误取第一条商品价格。
- 商户黑名单不把 `微信支付`、`支付宝`、`银联`、`Apple Pay`、`TAX INVOICE`、`RECEIPT`、`CASH SALE`、`支付成功` 等作为最终商户。
- 商户候选排序不因真实商户出现在支付渠道之后、金额之后或页面底部就被低优先级噪声覆盖。
- 脱敏外部增强开关关闭时，识别链路必须完全保持本地可用。
- 外部 API 开启时，金额仍以本地 `PaymentAmountExtractor` 为准，外部结果只能补充商户候选和解释。

验收：

- `bash scripts/run_offline_regression.sh` 通过。
- `bash scripts/run_golden_regression.sh` 通过。
- 新增核心解析类型不依赖平台框架。
- `LedgerTextInterpreterCore` 公共 API 不破坏。
- `ReceiptParser` / `SmartReceiptParser` 外部调用方式不破坏。
- 金额提取器和商户 resolver 可单独测试。
- debug trace 能看到金额候选、商户候选和 resolver 选中规则的简短信息。
- 外部大模型增强必须有单独开关、脱敏边界、失败降级和日志脱敏，不得作为默认识别路径。

## 5. 非目标

`v1.5.1` 暂不包含：

- 多账本正式模型
- `Ledger` / `ledger_id` 迁移
- 账本切换、账本归档、默认账本管理 UI
- 预算、投资、报销、协作账本
- 服务端账户系统
- 用高版本 availability 包住整个主链路来“假装支持低系统”

多账本继续顺延到 `v1.6.0+` 再重启评审。

## 6. 推荐实施顺序

### Phase A：版本与平台边界收口

- `v1.5.0` 标记为实现基线
- `v1.5.1` 接管当前开发线
- 把多账本从当前执行队列中继续排除

### Phase B：最低系统下调准备

- 审核 `AutoLedgerCore`
- 判断是否必须拆 `CoreBase`
- 列出每个 target 的 deployment target 修改清单
- 标出 `Apple Foundation Models` / `ControlWidget` 的 feature gate 边界

### Phase C：识别链路 Core 化重构

- 先落 `PaymentAmountExtractor` 与金额候选模型
- 再落 `RuleMerchantExtractor` / `MerchantResolver` / `MerchantNormalizer`
- 接入 `LedgerTextInterpreterCore` 并补离线回归
- 最后收敛 `ReceiptParser` / `SmartReceiptParser` 的金额和商户职责边界

### Phase D：脱敏外部 API 辅助识别试点

- 先定义脱敏请求 / 响应 schema
- 再新增 App 层外部解析 Adapter 与独立开关
- 将外部返回结果转成 `MerchantCandidate`，通过 `MerchantResolver` 合并
- 补充失败降级、日志脱敏和低置信度确认页边界

### Phase E：tvOS 第一版代码

- 先做总览页骨架
- 再补齐分类 / 趋势 / 摘要
- 接稳定只读数据入口

### Phase F：visionOS 第一版代码

- 先做 `WindowGroup` 骨架
- 再补四区展示
- 最后评估是否需要空间增强层

### Phase G：全平台截图与最终 smoke

- 补齐 tvOS / visionOS 截图资产
- 统一跑全平台 smoke
- 执行 Xcode Cloud / ASC 最终收口
