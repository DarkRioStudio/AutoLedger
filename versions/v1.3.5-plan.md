## 1. 版本定位

- 版本号：v1.3.5
- 承接版本：v1.3.4
- 版本主题：Worker API 评估 + 核心引擎批量验证
- 核心目标：
  - 评估将 `LedgerTextInterpreterCore` 部署到 Cloudflare Workers（或兼容 Swift 服务端运行时）的技术可行性、成本与收益。

  - 为 v1.4 Apple Watch 端和 v1.5 云端 Worker 生产化提供决策依据。

## 3. Track A：Worker API 评估

### 3.1 目标

评估将 `LedgerTextInterpreterCore` 部署到云端运行时的可行性，回答以下问题：

1. **运行时兼容性**：Core 的 Foundation-only 代码能否在 swiftwasm / Cloudflare Workers（Swift on WASM）或 Vapor + Linux 上无修改编译？
2. **性能**：单次解析延迟（不含 OCR）在服务端能否做到 <10ms p50？
3. **成本**：Cloudflare Workers 免费层（100k req/day）能否覆盖批量调参 + 实验性 API 调用？
4. **收益**：服务端批量调参对规则优化速度的提升是否值得维护一个额外运行时？

### 3.2 评估范围

需要迁移/打包的代码：

```
AutoLedgerCore/Sources/AutoLedgerCore/
  ├── Enums/
  │   ├── ReceiptSource.swift          ✅ 纯 Swift 枚举
  │   └── TransactionCategory.swift    ✅ 纯 Swift 枚举 + 推断方法
  ├── Models/
  │   └── LedgerInterpretationModels.swift  ✅ 纯 Swift 模型
  └── Services/
      ├── BillRelevanceGate.swift       ✅ Foundation-only（NSString）
      ├── LedgerTextInterpreterCore.swift ✅ Foundation-only（NSRegularExpression）
      └── VoiceLedgerParser.swift       ⚠️ 需检查 Foundation 依赖深度
```

不需要迁移：

- Vision OCR（保留在 App 侧）
- SQLite / LedgerStore（保留在 App 侧）
- Gemma / LLMProvider（保留在 App 侧）
- UIKit / SwiftUI / WatchConnectivity

### 3.3 候选运行时

| 运行时 | 优势 | 劣势 |
|--------|------|------|
| Cloudflare Workers (swiftwasm) | 全球边缘部署、免费层宽松、与现有 CDN 同一生态 | Foundation 支持有限（无 `NSRegularExpression`）、Swift 版本滞后 |
| Vapor + Linux Docker | Foundation 全兼容、可本地复现、成熟生态 | 需要维护服务器、无免费层、非边缘部署 |
| SwiftPM CLI (macOS/Linux) | 零额外成本、当前 batch_parse 已验证 | 无法弹性扩缩、不适合作为 API 端点 |
| Cloudflare Workers (JavaScript port) | 边缘部署、成本低 | 需要手动将 Swift 解析逻辑翻译为 JS，维护两个实现 |

### 3.4 评估方法

```text
1. 提取纯 Swift core 包
   - 从 AutoLedgerCore 中提取一个 `AutoLedgerCoreKit` 目录
   - 只包含：Enums/ + Models/ + Services/（不含 VoiceLedgerParser 中的 App 依赖）
   - 验证：swift build --target AutoLedgerCoreKit 在 macOS 通过

2. swiftwasm 编译试验
   - 安装 swiftwasm SDK
   - 尝试将 AutoLedgerCoreKit 编译为 WASM
   - 记录失败点（如果 NSRegularExpression 不可用，评估替代方案）

3. 性能基准
   - 用 batch_parse 跑 receiptsample 100 张样本
   - 记录 p50/p90/p99 解析延迟
   - 与 Cloudflare Workers 免费层配额对比

4. 决策记录
   - 输出 `tools/worker/EVALUATION.md`
   - 结论：GO / NO-GO / CONDITIONAL
```

### 3.5 输出物

- `tools/worker/EVALUATION.md` — Worker API 评估报告
- `tools/worker/` — Worker API 原型目录（如果 GO）
- `AutoLedgerCoreKit/` — 平台无关的 core 解析模块（仅含 Enums + Models + Services，不含任何 App 层依赖）
- `tools/receipt_ocr/batch_parse_server.swift` — 如果 GO，服务端批量解析脚本

## 4. Track B：核心引擎批量验证与扩增

### 4.1 receiptsample 全量基线

在 `receiptsample/scanned_receipts/data/` 全量样本上跑批量 OCR + 解析，生成基线报告：

```bash
bash scripts/run_receipt_batch_regression.sh \
  .tmp/receipt_ocr/scanned_receipts.ocr.jsonl \
  .tmp/receipt_ocr/scanned_receipts.parse.jsonl \
  .tmp/receipt_ocr/scanned_receipts.report.md
```

基线报告产出：
- 总样本数、金额命中率、商户非空率
- 置信度分布（high/medium/low）
- 非账单图片拦截数
- 分类分布
- 警告频率（missingAmount / merchantMissing / nonBillImage 等）
- Top 10 金额失败样本（手动标注根因）
- Top 10 商户失败样本（手动标注根因）

### 4.2 商户→分类映射表扩增

从批量报告中的高频率已知商户提取，分类映射从 7 组扩增到 ≥20 组。

扩增方向：

| 类别 | 新增商户 |
|------|---------|
| shopping | MR D.I.Y.、PERNIAGAAN ZHENG HUI、ABC HO TRADING、YONGFATT、SOON HUAT、INDAH GIFT |
| dining | McDonald's、KFC、Starbucks、Subway、Burger King、Pizza Hut |
| groceries | NTUC FAIRPRICE、WALMART、CARREFOUR、TESCO、AEON、LOTUS'S |
| transport | Grab、Gojek、Uber、EasyTaxi、公共交通卡 |
| digital | Netflix、Spotify、Apple One、Google One、iCloud+、ChatGPT |
| utilities | 电费、水费、燃气、宽带、手机话费 |

### 4.3 残余失败修复

基于全量批量报告，修复高频失败样本中可修复的模式。

常见失败模式（预期）：
- 商户名包含 OCR 拼接噪声（如地址行与商户名在同一行）
- 金额在小票中被分拆（如"Total\nRM 30\n.90"跨行）
- OCR 置信度低于 0.5 导致字段不可用

修复策略：
- 对于跨行金额：新增相邻行金额拼接逻辑
- 对于 OCR 噪声商户：新增行尾噪声过滤（如去除尾部符号/数字/地址片段）
- 对于低置信度样本：标记为 needsReview 而非直接失败

### 4.4 Apple Watch 编译验证

确认 `LedgerTextInterpreterCore` + `BillRelevanceGate` + `LedgerInterpretationModels` 在 watchOS target 下可编译：

```bash
xcodebuild -workspace AutoLedger.xcworkspace \
  -scheme AutoLedgerWatch \
  -destination 'generic/platform=watchOS' \
  build
```

如果当前没有 Watch target，至少验证 core 类型不依赖 iOS-only 框架（UIKit、Vision、AVFoundation 等）。

## 6. 验收标准

- Track A：
  - `AutoLedgerCoreKit` 可在 macOS 上通过 `swift build` 独立编译。
  - Worker API 评估报告 `tools/worker/EVALUATION.md` 包含：
    - 至少 2 个候选运行时的编译结果（成功/失败/原因）
    - 批量解析延迟 p50/p90（从 receiptsample ≥50 样本）
    - Cloudflare Workers 免费层配额对比
    - GO / NO-GO / CONDITIONAL 推荐
- Track B：
  - receiptsample 全量批量报告包含 ≥50 样本。
  - 商户→分类映射从 7 组扩增到 ≥20 组。
  - 新增 Golden Case ≥5 条（core 引擎）。
  - `bash scripts/run_offline_regression.sh` 通过。
  - `bash scripts/run_golden_regression.sh` 通过。
  - `xcodebuild -workspace ... -scheme AutoLedger -destination 'generic/platform=iOS' build` 通过。

## 7. Out of Scope

- 不上线生产 Worker API 端点（本版只做评估和原型）。
- 不修改 App Store 用户可见主流程。
- 不修改 SQLite schema。
- 不开始 Apple Watch target 实现（v1.4）。
- 不重构 `SmartReceiptParser` 或 `LedgerStore`。
- 不做 LLM-driven 规则增强。

## 8. 风险与应对

| 风险 | 应对 |
|------|------|
| swiftwasm Foundation 支持不足，NSRegularExpression 不可用 | 备选：Vapor + Linux Docker；备选：Swift 原生 String API 重写正则逻辑 |
| receiptsample 样本不足 50 张 | 降低基线标准，记录实际样本数；后续通过 feedback bundle 收集更多真实样本 |
| Track A 与 Track B 资源竞争 | Track A（Worker 评估）为探索性质，不阻塞 Track B（核心引擎加固）；两者可并行执行 |
| core 引擎在 watchOS 上 Foundation 行为差异 | 评估阶段只验证编译通过；行为差异留到 v1.4 真机验证 |
| 分类映射扩增导致误分类 | 先加 Golden Case 再加映射；映射只覆盖已确认识别的商户 |

## 9. 回滚方案

- Track A（Worker 评估）为新增目录和文档，不影响 App 主流程，可随时删除 `tools/worker/` 和 `AutoLedgerCoreKit/`。
- Track B（分类映射扩增和残余修复）可通过 git revert 恢复 v1.3.4 的 `LedgerTextInterpreterCore.swift`。
- 批量基线报告输出到 `.tmp/`，不进入 Git。
