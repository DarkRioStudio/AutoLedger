## 已确认的代码问题与修复范围

1. 扫描端实际发送 `flow_type=receipt_scan`、`input_type=live_ocr`，Worker 却只检查 `flow_type=live_ocr`。Core 与 Worker 统一识别实际字段，并兼容旧 flow 拼写；普通导入只统计非实时扫描终态。错误分布只统计失败终态，修复成功事件的 `error_code=none` 被显示为 9 条“导入错误”的问题。
2. 汇总把 hang 归入“系统崩溃”，又在“慢操作”重复展示。现在分别显示 crash、hang、应用慢操作和系统性能诊断；保留系统诊断与挂起计数存在重叠的说明，不改变原始事件。
3. 启动时无条件写 active，会使后台唤醒也留下活跃会话标记。改为先消费前次标记并记录 launching，仅在 App 聚合 scenePhase 进入 active 时写活跃；全部窗口后台时标记 clean。不能据此宣称历史 115 条均是误报。
4. 后台快照读取前仍在 MainActor 执行缺失账本币种的 UPDATE。将原操作移入已有独立 SQLite 连接，与快照一起在后台完成；保留币种补齐、并发编辑后重试及失败保留内存状态的语义。

- 本轮读取的都是旧 binary 样本；修复效果需要新 1.9.0 开发线 binary 和后续真实样本验证。
- 聚合数据没有堆栈，尚不能定位 1.7.0(132) 的 MetricKit hang 根因；需要对应来源构建的 Organizer / Instruments 诊断。
- 移除主线程数据库操作是局部改善，不能证明它造成了已观测的 3–10 秒刷新。真机前台切换、后台唤醒、多窗口和大账本回读继续保留设备验收。
- Worker 源码验证、部署和线上读回分别记录；App 本地构建不等于 Archive、TestFlight 或商店发布。
